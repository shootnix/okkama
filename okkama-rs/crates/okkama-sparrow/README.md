# Sparrow: байткод и верификатор

Независимый crate без внешних зависимостей. Его используют генератор
`okkama-compiler/src/codegen/sparrow` и самостоятельный исполнитель
`sparrow-vm`. Совместимый адаптер находится в `okkama-runtime/src/sparrow`.
VM не зависит от компилятора. Бинарник `sparrow` поставляется crate `sparrow-cli`.

## Запуск

Из `okkama-rs`:

```sh
cargo run --offline -p okkama-cli -- run --engine sparrow examples/sparrow-control-flow.ok
cargo run --offline -p okkama-cli -- build examples/sparrow-control-flow.ok --target sparrow -o out.spb
cargo run --offline -p okkama-cli -- exec out.spb
cargo run --offline -p sparrow-cli -- check out.spb
cargo run --offline -p sparrow-cli -- out.spb
```

Пример возвращает 42 как код выхода процесса. Файл исполняется без исходников
и Java. Обычный `run` пока исполняет через JVM; `--engine sparrow` — эта VM. Библиотечный исполнитель
возвращает точное целое хосту, а CLI требует результат main в диапазоне 0..255.

Поддерживаются int/bool, +/−/*/%/унарный минус, сравнения, bool not/equality,
ветвления и циклы, параметры блоков, прямые синхронные вызовы и возвраты
int/bool/string/object/void, а также `trap`. Поддерживаются строковые операции,
обычные объекты, конструкторы, defaults, методы и successor, типизированные
массивы (включая вложенные), size/get/slice, ленивый lookup, split/join.
Вызовы исполняются собственным стеком кадров;
рекурсия глубиной 20 000 проверяется без рекурсии Rust-исполнителя.
Свободные helper-функции тестируются на IR: их исходный синтаксис язык не требует.

Генератор проверяет IR и компилирует все функции, переставляя main первым и
перенумеровывая вызовы. Отсоединённые блоки после return/last не попадают в
код; достижимость учитывает обе стороны cond и не вычисляет его константность.
Остальные неподдержанные инструкции и объявления дают ошибку. Lifecycle, остальные
native-функции и полная упаковка импортов ещё требуют расширения
Sparrow. [План реализации](../../docs/sparrow-runtime-roadmap.md).

## Значения, переходы и функции

`Program` содержит общий пул точных целых констант, код, верхнюю границу
номеров регистров, таблицы функций и типов объектов. Целые — каноническая десятичная запись
без ограничения разрядности; bool — отдельный тип.

Пустая таблица функций означает один main: вход 0, без аргументов, результат
int (SPB v1). Непустая таблица содержит все функции, main первой. Входы идут
строго по возрастанию, разделяя код на непересекающиеся диапазоны.
Каждая сигнатура задаёт регистры параметров, их типы и тип результата либо void.
Регистры локальны кадру, даже если их номера совпадают у разных функций.

`Target` содержит индекс инструкции и пары `(назначение, источник)`.
Перед переходом VM сначала читает ВСЕ источники, затем пишет назначения.
Так обмен `(r0, r1) = (r1, r0)` сохраняет оба значения. Условный переход
вычисляет condition до записи параметров и применяет только выбранное ребро.
Обычный переход не может пересекать границу функции; для этого есть call.

Верификатор проверяет границы регистров/констант/функций, сигнатуры вызовов,
типы операций и return, отсутствие повторных назначений на одном ребре,
падения за конец функции и недостижимых инструкций. Для каждого блока
вычисляет пересечение состояний всех предшественников до неподвижной точки,
включая обратные рёбра. Чтения проверяются после сходимости. Указание огромного
register_count не вызывает соответствующую аллокацию.

Анализ ограничен 1 000 000 сохранённых пар регистр/тип и 4 000 000 единиц работы
на функцию. При превышении возвращается диагностическая ошибка. Эти лимиты
защищают анализ; лимит файла не является лимитом памяти исполняемой программы.
Допустим бесконечный цикл: верификатор проверяет безопасность формы, не завершение.

`undef` — типизированная заглушка lowering для ещё не полученного результата
цикла. Её можно переносить по рёбрам; чтение как int/bool возвращает runtime
error. Lowering направляет путь отсутствующего результата к `trap`.
`trap` возвращает ошибку Rust-хосту, не завершает процесс внутри библиотеки.

## Бинарный формат

Все числовые поля big-endian. Rust layout не является форматом файла.
Лимит файла — 16 MiB (`MAX_FILE_BYTES`); encode и decode проверяют программу.
Counts и длины проверяются по оставшимся байтам до выделения коллекций.
Неизвестные версии, flags, теги, некорректный UTF-8 и лишние байты отклоняются.

| Смещение | Поле |
|---|---|
| 0 | 4 ASCII-байта `SPRW` |
| 4 | версия `u16`: 1, 2, 3, 4, 5, 6, 7 или 8 |
| 6 | flags `u16`: 0 |
| 8 | граница номеров регистров `u32` |
| 12 | число целых констант `u32` |
| 16 | число инструкций `u32` |

В v1 сразу следуют константы. В v2 на смещении 20 находится число функций
`u32`, затем записи: `entry u32`, `result u32`, `parameter_count u32`, пары
`register u32, type u32`. Теги сигнатур: 0 = void (только результат),
1 = int, 2 = bool, 3 = string, 4 = byte, 5 = char, `0x40000000 | id` = объект с индексом id
в таблице типов (младшие 30 бит). Таблица v2 не может быть пустой.
Writer выбирает v1 для пустой таблицы функций и v2 для непустой, если нет
объектов. Старые файлы v1/v2 продолжают читаться.

При наличии объектов writer выбирает v3. После таблицы функций (она может
быть пустой для единственного неявного main) идут `object_count u32`, затем
для каждого объекта `field_count u32` и теги типов полей. Индекс записи —
идентификатор типа; ссылки на другие объекты, включая рекурсивные объявления,
проверяются до исполнения. После этой таблицы идут обычные константы и код.
Методы представлены функциями, получающими receiver первым аргументом.
Таблица v3 не содержит destroy/native-объекты: их codegen пока отклоняет.

При наличии типов массивов writer выбирает v4. После таблицы объектов идут
`array_type_count u32` и по одному тегу типа элемента для каждой записи.
Тег массива — `0x80000000 | id`. Вложенный тип массива обязан ссылаться на
более раннюю запись: циклы в этой таблице отклоняются. Объекты могут содержать
массивы и наоборот. Таблица объектов в v4 может быть пустой. Старые версии
файлов сохраняют свою кодировку и продолжают читаться.

Внутренний builder использует тег `0xc0000000 | id`, где id указывает на тип
элемента в таблице массивов. Builder нельзя хранить в полях объектов или
элементах массива. VM хранит неизменяемые узлы builder: push/append возвращают
новую версию, finish собирает массив итеративно. Линейность builder в исходном
IR проверяется до генерации байткода; сырые копии handle в VM не изменяют
предыдущую версию. Новые теги и opcode требуют актуального reader.

При наличии ролей или witnesses writer выбирает v5. После таблицы массивов
идут `role_count u32`, для каждой роли `method_count u32` и записи методов:
`result u32, parameter_count u32`, затем теги параметров без receiver.
Далее `witness_count u32` и записи `object u32, role u32, slot_count u32`,
затем индексы функций по слотам роли. Тег роли — `0x20000000 | id`
(младшие 29 бит), в сигнатурах, Undef и Copy.

Verifier проверяет уникальность пары object/role и точную сигнатуру каждого
метода: receiver соответствующего объекта, параметры и результат роли.
RoleWrap и RoleNarrow сохраняют тот же объект; сужение требует номинального
witness целевой роли, иначе вызывает trap. CallRole выбирает функцию по
фактическому типу объекта. Старые версии v1–v4 сохраняют свою кодировку.

При наличии enum writer выбирает v6. После таблиц v5 идут `enum_count u32`
и число вариантов `u32` для каждого номинального типа. Имена не нужны для
исполнения: значение хранит индекс типа и индекс варианта. Тег типа —
`0x10000000 | id` (младшие 28 бит), включая сигнатуры, Undef и Copy.
Verifier проверяет индексы, границы вариантов и одинаковые типы операндов
EnumCompare; допустимы только Eq/Ne. Старые файлы v1–v5 продолжают читаться.

При наличии обработчиков writer выбирает v7. После таблицы enum идут
`handler_count u32`, затем записи `start u32, end u32, failure_register u32`
и обычный Target (индекс инструкции, число пар dst/src, пары регистров).
Диапазоны `[start, end)` упорядочены и не пересекаются; диапазон и цель
принадлежат одной функции. Failure имеет тег сигнатуры 6 и тег Undef 5.

Исключительное ребро использует состояние регистров ДО инструкции.
Параллельные аргументы перехода копируются до записи failure_register;
этот регистр не может дублировать назначение аргумента. Verifier проверяет
все такие рёбра вместе с обычными переходами и лимитирует объём анализа.
VM ищет обработчик текущей инструкции, затем поднимается по кадрам вызовов.
Raise продолжает распространение, FailSecondary сохраняет первичный отказ,
FailCaused сохраняет причину нового типизированного отказа. Panic, Trap и
NativeCall используют общий механизм.

При наличии метаданных Error writer выбирает v8. После таблицы обработчиков
идут `error_role u32`, `native_object u32` (u32::MAX означает отсутствие),
`object_name_count u32` и имена всех объектов в порядке таблицы: длина u32 и
UTF-8. Error обязан иметь ровно один слот text() → string. NativeFailure,
если объявлен, имеет четыре string-поля и witness Error; ObjNew/ObjNext для
него запрещены. Такой объект создаёт только runtime.

Throw проверяет статический тип Object/Role, делающий Error. Catch получает
failure, тип обработчика, регистр payload и две цели. Payload определён
только на совпавшей ветви; аргументы перехода снимаются до его записи.
Неперехваченный объект вызывает настоящий text() после unwind, в той же куче.
Метаданные имён и методов обеспечивают диагностику без исходников.

Битовые операции int работают со словом signed-64. IntShr сохраняет знак,
IntUshr заполняет старшие биты нулями; результат также интерпретируется как
signed-64 (поэтому `-1 >>> 0` равно `-1`). Число позиций проверяется точно:
вне `0..63` возникает ошибка `Shift count must be in 0..63`, без маскирования
или усечения большого целого счётчика. Все операнды и результаты имеют тип int.

Range — неизменяемое значение с тегом сигнатуры 7 и тегом Undef 6.
Оно хранит исходные границы и признак включения конца; равенство сравнивает
все три компонента. RangeNew отвергает убывающие границы. RangePart для
включительного конца возвращает точное `end + 1`, без signed-64 переполнения.
Lowering использует это же правило для внутреннего шага счётчика цикла;
обычная пользовательская арифметика int сохраняет своё переполнение.

Convert поддерживает int/bool/byte → string и byte → int. ByteFromInt
проверяет точный диапазон без усечения; ошибка сохраняет контекст аргумента
`@byte(...)`. Bool преобразуется в строки `"1"` и `"0"`. LoadChar отвергает
суррогаты и значения выше U+10FFFF. StrUtf8 кодирует все Unicode scalar values,
включая NUL; операция сама не добавляет BOM.

BuilderAppendRange добавляет точные целые `[start, end)` либо `[start, end]`.
Границы не сужаются до машинного целого; start > end вызывает runtime trap.
При равных границах результат пустой либо содержит один элемент.

Побитовые byte-операции сохраняют тип byte. При сдвиге влево выходящие биты
отбрасываются; правый сдвиг заполняет нулями. Для byte обе формы Okkama `>>`
и `>>>` компилируются в ByteShr. Счётчик проверяется как точное целое в 0..7,
без маскирования/усечения; иначе возникает `Shift count must be in 0..7`.

NativeCall использует [общий ABI](../okkama-runtime-abi/README.md): ID определяет
сигнатуру и результат. `byte array type id` обязан указывать на элемент byte;
он связывает ABI `@byte` с таблицей типов программы. Verifier проверяет число
аргументов и их типы. Генератор создаёт для native-декларации обычную функцию
из NativeCall и Return, поэтому межфункциональные вызовы сохраняют общий ABI
кадров. Provider встроен в VM, исходники `.ok` во время выполнения не нужны.

Строковые литералы находятся непосредственно в инструкции LoadString, целые
по-прежнему в пуле констант. Срезы проверяют точные индексы без усечения.
Trim использует Unicode White_Space; chomp удаляет ровно один CRLF/LF и сохраняет одиночный CR (D-033).
Replace выполняет буквальную замену непересекающихся вхождений, включая
пустой шаблон на границах code points.

ObjNext создаёт новый объект, не меняя старый и его алиасы. Вложенные handles
сохраняются. Copy не преобразует тип. Verifier проверяет тип receiver,
порядок и типы полей, границы индексов и отсутствие повторов в обновлениях.

Target: индекс инструкции, число пар, затем пары dst/src. Comparison:
0 Eq, 1 Ne, 2 Lt, 3 Le, 4 Gt, 5 Ge; для bool разрешены только Eq/Ne.
Коды 1–5 сохраняют прежнюю кодировку. Старые загрузчики отклоняют незнакомые
opcodes/версию; нового кода под видом старого они не исполняют.

ArrayLookup сначала читает индекс и все аргументы выбранного перехода, затем
выполняет параллельные присваивания. Только на found-ребре после них записывает
payload dst. Verifier не считает этот регистр инициализированным на missing-ребре;
payload dst не может совпадать с назначением found-аргументов. Отрицательный,
слишком большой и отсутствующий индекс выбирает missing, а обычный ArrayGet
возвращает ошибку. Срезы проверяют точные индексы и копируют handles элементов.

Ошибки кодека содержат смещение байта, когда оно известно; ошибки verifier/VM —
индекс инструкции. Source map пока отсутствует.

```rust,ignore
let program = okkama_compiler::codegen::sparrow::generate(&module)?;
let bytes = okkama_sparrow::encode(&program)?;
let loaded = okkama_sparrow::decode(&bytes)?;
let result = okkama_runtime::sparrow::execute(&loaded)?;
```

## Проверки

```sh
cargo test --offline -p okkama-sparrow -p okkama-runtime
cargo test --offline -p okkama-cli --test cli
```

Тесты покрывают сквозной путь исходник → IR → SPB → VM, все сравнения,
короткое замыкание, next/last, обмен параметров на обратном ребре, loop traps,
int/bool/void вызовы, продолжение после вызова и глубокую рекурсию.
Отдельно проверяются подмена типов на ветвях/циклах, чтение до инициализации,
неверные сигнатуры/границы функций, усечённые файлы, враждебные counts и
мутации байтов. CLI исполняет файл с пустым PATH, без доступа к Java.

## Структурное равенство

ValueCompare проверяет одинаковые статические типы и Eq/Ne. Общий алгоритм
runtime-core сравнивает массивы по длине и порядку элементов, обычные объекты
по конкретному типу и всем полям, включая private. Ролевая ссылка сохраняет
это правило для фактического объекта; сравнение не вызывает методы.

Обход итеративный, с запоминанием уже проверяемых пар объектов/массивов.
Это устраняет рекурсию Rust и повторный обход общих подструктур. Скалярные
категории не смешиваются; внутренние Failure/Builder и Undef не сравниваются.
NativeFailure сравнивается по своим неизменяемым полям. Opcode требует
актуального reader, без изменения существующих таблиц формата.
