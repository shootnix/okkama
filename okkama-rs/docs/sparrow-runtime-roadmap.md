# Rust runtime, Sparrow, GC и JIT

Цель: исполнять Okkama в Rust-процессе двумя независимыми движками — IR-
интерпретатором и VM Sparrow — с той же семантикой, что у JVM-пути, и
собирать автономный байткод Sparrow.

## Состояние — 24 октября 2026: паритет с JVM

IR-интерпретатор и Sparrow исполняют весь язык и всю std: каждая программа
репозитория выполняется через `--engine ir` и `--engine sparrow` с теми же
stdout, stderr и кодом выхода, что и через JVM.

| Проверка | JVM | IR | Sparrow |
|---|---|---|---|
| OCS `full-release` (772 обязательных) | 772/772 | 772/772 | 772/772 |
| std (237 файлов с тестами, `-t`) и examples (422 программы с `main`) против JVM | эталон | совпадают все детерминированные | совпадают все детерминированные |

Недетерминированные программы (время, случайные числа, порты, порядок
печати конкурирующих задач — у JVM они тоже различаются между прогонами)
сверены вручную. Оставшиеся известные расхождения с JVM — в
[compatibility.md](compatibility.md#движки-ir-и-sparrow-расхождения-с-jvm).

Устройство:

- Общий рантайм `okkama-runtime-core`: значения (Rc), точные целые,
  float/rat, коллекции, равенство, регионы и `destroy`, отказы, планировщик
  задач на сопрограммах, intrinsics `async/*` и `test.*`, все natives
  `std/runtime/*` (528 по ABI `okkama-runtime-abi`), протокол воркеров
  `spawn`, операции над значениями `ops` (их вызывают оба движка, как
  JVM-байткод — `okkama.rt`).
- IR-интерпретатор (`okkama-runtime`) исполняет OIR-1 напрямую.
- Sparrow: генератор OIR → SPB 9 (`codegen/sparrow`), модель, кодек,
  верификатор и ассемблер (`okkama-sparrow`), VM (`sparrow-vm`), отдельный
  бинарник `sparrow` (`sparrow-cli`). Формат и набор инструкций —
  [sparrow-isa.md](sparrow-isa.md).

```sh
okkama run --engine ir|sparrow|jvm [-t] app.ok [ARGS...]   # OKKAMA_ENGINE — умолчание
okkama build app.ok --target sparrow [-t] -o app.spb
okkama exec app.spb [ARGS...]                              # или sparrow app.spb
sparrow test app.spb
sparrow --disassemble app.spb -o app.spa
sparrow --assemble app.spa -o app.spb
python3 tools/engines/parity.py --engines ir,sparrow       # паритет с JVM
cd ../conformance && ./ocs run --adapter adapters/rust/adapter.json \
    --profile full-release --adapter-env OCS_RUST_ENGINE=sparrow -j 8
```

`okkama run` по умолчанию исполняет IR-интерпретатором (с 25.10.2026; до
этого — JVM); `--engine sparrow|jvm` или `OKKAMA_ENGINE` выбирает другой.

## Следующий этап — после паритета

Порядок согласован с пользователем (24.10.2026): сначала полнота, затем:

1. **Рекурсия → цикл** — сделано для хвостовых самовызовов (24.10.2026):
   OIR-проход `okkama-compiler/src/ir/recursion.rs` заменяет
   `r = call F(args); ret r` в самой `F` переходом к началу тела (вход
   функции становится переходом к блоку-циклу с новыми параметрами), для всех
   движков. Нехвостовая рекурсия ограничена памятью: IR и Sparrow держат кадры
   в куче (JIT без запаса стека уходит в интерпретатор), JVM исполняет
   программу в потоке со стеком 4 GB. Дальше: взаимные хвостовые вызовы и
   накопитель для `n * f(n - 1)`-форм.
2. **Бесконечная рекурсия на этапе анализа** — сделано (24.10.2026, §11.6.1):
   действие ошибочно, если ни один путь от входа не завершает его (результат,
   отказ или операция, которая может отказать), не вызвав сначала функцию той
   же группы рекурсии (наибольшая неподвижная точка над компонентами сильной
   связности графа прямых вызовов). Анализ консервативен: вызовы вне группы,
   `await`, деление и т. п. считаются возможным завершением.
3. **GC** — сделан (раздел ниже).
4. **JIT** — сделан (раздел ниже).

Покрытие необходимо сверять с `InstKind`, `TermKind`, типами и native-
реестром, а не только с числом зелёных тестов. Общая регрессия:

```sh
cargo test --offline --workspace
```

## GC — сборщик циклов (реализован 24.10.2026)

Значения обоих движков — `Rc` с итеративным освобождением: недостижимое
освобождается сразу. Значения неизменяемы, поэтому цикл ссылок замыкает только
ребро, записанное после создания узла: позднее поле (`obj.init`, когда `self`
ушёл значением из конструктора), состояние intrinsic объекта std (канал,
Atomic, Retained, хранилище fake, таймаут), исход Future, причина и вторичные
отказы `Failure`, содержимое builder. Неизменяемые рёбра ведут к более старым
узлам и цикла не образуют.

`okkama-runtime-core/src/gc.rs` — общий для IR и Sparrow сборщик пробным
удалением (trial deletion, как сборщик циклов CPython):

1. Кандидаты — узлы, получившие позднее ребро (слабые ссылки):
   `Object::init`/`set_intrinsic`, `sched::complete` с исходом-ссылкой.
2. Подграф — узлы, достижимые из кандидатов по точно перечисленным сильным
   рёбрам (объекты, массивы, словари, замыкания, `any`, Future, Failure,
   builders, состояния intrinsics).
3. Внешние ссылки узла = `strong_count` − рёбра подграфа − наша копия; узел
   с внешними ссылками — корень, достижимое из корней живо.
4. У мусорных узлов очищаются поздние рёбра; остальное освобождает `Rc`.

Неперечисленный держатель (кадры исполнителей, корутины, замыкания рантайма,
регионы, native handles) делает цель «внешне достижимой»: сборщик
консервативен — может не найти мусор, но не освобождает живое. Заимствованное
состояние (`RefCell`) в этот момент считается корнем. Корни не регистрируются,
safepoints не нужны: сборка идёт при регистрации кандидата.

Темп: сборка, когда новых кандидатов не меньше `max(4096, выживших,
узлов прошлой сборки / 8)` — амортизированно O(1) на кандидата.
`OKKAMA_GC=off` выключает сборщик (для сравнения). `destroy` по-прежнему
управляется регионами, а не достижимостью: сборщик освобождает только память.

Измерения (1 млн циклов `Owner ↔ Child` через `obj.init`; 1 млн
`Atomic ↔ Node` через intrinsic): пиковая память 536 MB → 11 MB и
521 MB → 13 MB на обоих движках; время на худшем случае (цикл в каждой
итерации) +13%.

## JIT — машинный код Sparrow (реализован 24.10.2026)

`sparrow-vm/src/jit.rs`, Cranelift 0.137. Горячая функция (1000 вызовов или
обратных переходов; `OKKAMA_JIT=eager` — с первого вызова, `off` — выключен,
`OKKAMA_JIT_DEBUG` — журнал компиляции) компилируется целиком.

- Регистры машинного кода — те же слоты `Value` кадра (`Value` —
  `repr(C, u8)`, 24 байта; теги читаются с образцов при старте). Поэтому вход
  возможен в начале функции и в любой цели перехода: обратный переход
  интерпретатора в скомпилированной функции продолжает её машинным кодом (OSR).
- Быстрые пути в коде: константы (любые: скаляры словами, остальные —
  копией готового значения), копии, `int.add/sub/mul/mod/cmp` малых целых
  (переполнение signed-64 — точный помощник, R01), `float.add/sub/mul/div/
  neg/abs/cmp` (неконечный результат и деление на 0 — помощник с ошибкой
  программы), переходы по `bool` и записи рёбер, возврат, `obj.get`,
  `arr.get`/`arr.len`, `role.wrap`/`role.narrow` (бит карты «объявление
  делает роль» из таблиц программы). Раскладки `Value`, `Rc<Object>` и
  `Rc<Array>` читаются с образцов при старте; не распознана — помощник.
- Вызовы: прямой `call` через таблицу кода; `call.role` — помощник только
  находит цель (реализации слота известны из таблиц, регистры — в кадре под
  наибольшую), дальше как прямой; `call.fn` — то же для целей из `fn.closure`
  программы (помощник пишет захваты и аргументы в регистры вызываемой).
- Живость регистров (`liveness.rs`, обратный поток по инструкциям с рёбрами
  отказа): последнее использование — перемещение, а не копия (аргументы,
  `move`, записи рёбер, поля `obj.new`, `builder.push`, `obj.next`).
  Поэтому у `x = x.succ()` старый объект остаётся единственной ссылкой, и
  `obj.next` обновляет его на месте (`ObjectHeap::successor_owned`: только при
  единственной ссылке, без слабых ссылок сборщика, поздних полей и
  региона-владельца) — без выделения и копии неизменённых полей. При любом
  псевдониме — обычная копия, наблюдаемо одинаково.
- `OKKAMA_JIT_STATS=1` печатает, какие инструкции и сколько раз ушли в
  помощники (и сколько `obj.next` прошли на месте).
- Остальные инструкции — помощники над тем же `evaluate` интерпретатора,
  поэтому семантика одна. Вызовы natives/intrinsics/async/`call.fn`/
  `call.role`, закрытие регионов (`destroy` вложенно) — помощники.
- Отказ: помощник кладёт его в контекст и возвращает `RAISE`; обработчик
  диапазона инструкции принимает его в коде, иначе отказ уходит вызывающему
  с местом возникновения. Ошибка исполнителя — `FATAL` с местом.
- `await` приостанавливает корутину внутри помощника: задачи стековые, кадры
  машинного кода остаются на стеке задачи. Планировщик сообщает нижнюю границу
  текущего стека; без запаса 4 MB вложенный вызов исполняет интерпретатор
  (кадры в куче), поэтому глубина рекурсии ограничена памятью, как без JIT.
  У кода JIT нет таблиц раскрутки: незавершённая задача с машинными кадрами
  при завершении запуска сбрасывается без раскрутки; паника Rust в помощнике
  перехватывается и становится ошибкой исполнителя.

Измерения (release, Apple M2 Max, `benchmarks/`): см. раздел «Бенчмарки».
