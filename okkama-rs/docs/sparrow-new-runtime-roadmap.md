# Новый Sparrow с нуля: runtime, JIT и async на Tokio

Статус: активный план. Согласовано 2026-11-03, ветка `nom`.

## Обязательный порядок работы

Перед началом работы и после каждой задачи читать
[порядок выполнения и текущий шаг](new-runtime/execution-order.md).
Следующую задачу выбирать по этому порядку и зависимостям, а не по последней
записи журнала или наиболее удобному незакрытому native-провайдеру.
Критерии приёмки фаз остаются в этом roadmap; порядок не ослабляет их.

## Цель и границы

Создать новую быструю самостоятельную машину Sparrow для Okkama: минимизировать
аллокации, проектировать исполнение под JIT и обеспечить полноценную асинхронность
на готовом Rust-бэкенде. Это переписывание ядра, а не дальнейший тюнинг старого
runtime и не переименование его копии.

Итог: все возможности Okkama реализованы новым runtime, совместимость подтверждена
полным conformance и проверками stdlib, examples и остальных программ репозитория.
Только после этого — сравнительные бенчмарки старый Sparrow / новый Sparrow.
Ориентир последующей работы для SQL/DB: не более 1.5× времени Python на одинаковой
работе; 0.5× — желаемая дальнейшая цель, не обещанный результат переписывания.

Малый размер языка сам по себе не гарантирует скорость. Основные проектные
критерии — представление значений, стоимость вызова, размещение объектов,
приостановка задач и границы native-кода.

  сверяться с ним; обновлять после завершения работы, а не только в конце проекта.
- `[x]` означает реализацию и проверку критерия приёмки. В журнале указывать
  артефакт/коммит, команды, результаты и оставшиеся ограничения.
- Частично реализованная фаза остаётся `[ ]`; закрывать можно отдельные подпункты.
- Нельзя закрывать фазу на основании плана, наличия каркаса, микробенчмарка или
  работы только на удобном подмножестве языка.
- Не возвращаться к экономии отдельных аллокаций старого runtime, изменениям
  SQL-обвязок или замене библиотек вместо строительства нового ядра.
- Уже сделанный scalar-replacement POC — исследовательское свидетельство,
  а не реализация новой машины. Существующий `sparrow-runtime` пока является
  копией прежнего ядра; его выделение не закрывает фазы ниже.
- Старый runtime остаётся эталоном поведения. Новый не должен тайно выполнять
  неподдержанный код через него. На промежуточных этапах — явная диагностика
  неподдержанных инструкций; в финале для поддерживаемой Okkama таких пробелов нет.
- Сначала совместимость, затем сравнительные бенчмарки. Просмотр машинного кода,
  проверки корней и числа аллокаций допустимы как проверки реализации; не подменять
  ими завершение runtime и не запускать новый цикл соревнования микробенчмарков.

## Зафиксированные архитектурные решения

1. Самостоятельные значения, память, кадры и исполнение Sparrow. Нет зависимости
   от IR-интерпретатора, старого `Value`, `Rc<Object>`, `Region` и `sched.rs`.
   Общие независимые native-библиотеки и декларативный ABI можно переиспользовать.
2. JIT получает типизированные SSA-значения. Числа и bool не упаковываются в
   универсальный контейнер при каждой операции. Компактное динамическое
   представление необходимо только там, где требуется динамическая граница.
3. Объекты по возможности устраняются инлайнингом и scalar replacement. Для
   неубегающих материализованных объектов рассматривается стек. Куча остаётся
   для данных, которым нужна более долгая жизнь; её минимизируем, не запрещаем.
4. Объект и поля размещаются вместе там, где это подходит представлению. Нет
   обязательного отдельного Vec для каждого объекта, набора аргументов и вызова.
5. Машинное соглашение вызовов проектируется вместе с кадрами и JIT. Регистры
   байткода и CPU-регистры — разные понятия; физические регистры распределяет
   backend, а spills имеют определённое время жизни и видимость для GC.
6. Нет графовых обходов при каждом переносе владения обычным значением. Управление
   памятью отделено от языкового cleanup ресурсов. Корни, safepoints и native
   handles определяются до реализации сборщика. Конкретный GC выбирается в фазе 3;
   поколенческий или перемещающий GC не добавляется автоматически ради названия.
7. Async обязателен с начала проектирования: продолжение содержит точку исполнения
   и живые значения. Отдельный стек корутины на каждый async-вызов не является
   основой новой машины. Значение через await нельзя оставлять в умершем кадре.
8. Rust `Future`/`Poll`/`Waker` — граница адаптера; Tokio — executor, I/O, таймеры,
   очереди пробуждения и готовые примитивы. Не пишем свой executor/reactor.
9. Обычный await не равен `tokio::spawn`: вложенное ожидание по возможности
   исполняется внутри одной задачи. Моменты запуска задаёт семантика Okkama.
10. Первоначально VM-объекты исполняются локально; не навязываем всем объектам
    Send/Sync и Arc. Между native-потоками передаются явно принадлежащие им данные.
    Блокирующие операции изолированы от executor. Для SQLite сохраняется отдельный
    подход к прерыванию: начатый spawn_blocking не отменяется обычным abort.
11. Tokio не реализует семантику Okkama автоматически. Адаптер сохраняет холодные
    Future, порядок старта, повторное ожидание и сохранённый результат, Cancelled,
    defer, cleanup и распространение ошибок. Отмена не сводится к JoinHandle::abort.
12. Native-граница принимает простые значения и непрозрачные handles. Не допускаем
    промежуточного преобразования через старые VM-объекты между каждым слоем.

Основание для async-границы: [Rust Future](https://doc.rust-lang.org/std/future/trait.Future.html),
[Tokio async](https://tokio.rs/tokio/tutorial/async),
[Tokio tasks и cancellation](https://docs.rs/tokio/latest/tokio/task/),
[spawn_blocking](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html).
Версии зависимостей и конкретный вариант локального executor фиксируются при реализации.

нельзя ослаблять тесты, чтобы назвать переписывание завершённым.

Фазы 1–3 сразу проектируются с учётом этой фазы; async не прикручивается к готовому
синхронному heap постфактум. Рабочая интеграция может идти параллельно развитию типов,
но каждый подпункт закрывается только после собственных проверок.

- [ ] Фаза завершена: вся async-семантика Okkama работает через готовый Rust-бэкенд.
- [ ] Подключить Tokio и определить владение runtime, запуск и shutdown.
- [x] Tokio 1.54.1 current-thread/LocalSet host, Rust Future bridge, таймерный driver
      и cooperative JIT/cold budget; без собственного executor и стековых корутин.
- [x] Холодные async-вызовы и повторный await готового значения/отказа;
      10 000 вложенных await через плоские продолжения, с GC.
- [ ] Реализовать lowering async-функций в продолжения с живыми через await значениями.
- [ ] Реализовать Sparrow Future как адаптер Rust Future/Poll/Waker; ready fast path,
      Pending, пробуждение и повторный вход без собственного executor/reactor.
- [x] Local fut.spawn через Tokio: eager-start handshake, 2000 вложенных spawn,
      несколько ожидающих, кэш результата/отказа, первые shutdown/cleanup probes.
- [ ] Холодные Future, запуск до первой приостановки там, где этого требует контракт,
      spawn, повторный await, сохранение результата и нескольких ожидающих.

- [x] Parked task GC roots, generic typed task results, Tokio watch completion

- [x] Semaphore/Permit: FIFO через Tokio admission, весь диапазон i64 capacity,

### 2026-11-06 — SQLite-драйвер на новом runtime и первый DB-профиль

По решению пользователя дорожка накладных расходов переключена на исходную цель —
SQL/DB. `native_sqlite.rs`: все 44 функции `runtime/database@1::sqlite_*` на
rusqlite 0.37 (bundled), без зависимости от старого runtime (boundary guard
разрешает). Ядро Engine перенесено из эталона почти дословно (cursor/prepared,
bind, батчи fetch ≤64, лимиты, authorizer, blob, backup, script); Engine создаётся
и живёт в рабочем потоке соединения, через границу потока ходят только Send-данные,
поэтому `unsafe impl Send` не нужен. Запрос — `native_io` Future с hook отмены:
interrupt + ожидание ответа; удавшаяся отменённая операция освобождает cursor,
prepared, BLOB или backup. autocommit/broken рабочий поток пишет в атомики.
Строки отдаются программе как DB cells. Отличие от эталона: с bundled SQLite
rusqlite отдаёт ошибки prepare как `SqlInputError`; эталон их не разбирал
и сообщал синтаксис как `unexpected`, новый провайдер берёт вид по коду SQLite.
Второй unsafe-модуль движка (после jit.rs) — самоссылающийся cursor и C API
authorizer/BLOB/backup, как в эталоне.

Проверки: 2 unit-теста провайдера (типизированные cells через prepared, батч
и eof, закрытый reply; транзакция через control, отказ SQL с kind, отмена
открытия cursor с последующей работой соединения, запрос после close).
15 conformance-кейсов с `db/sqlite` (L11 ×10, L12 ×2, L13 ×3, собраны okkama
0.3.4 со стандартной библиотекой HEAD и harness) — PASS на origin и next.
Тест `every_supported_abi_signature_loads…` исправлен: handle берёт модуль-владелец
(`DbCellState` из `runtime/db`), таблица вынесена в `native::handle_module`.

`benchmarks/db` (5000 строк, 500 lookup), профиль и исправления:
- GC: после пика (28 тыс. живых) арены оставались большими, а порог падал до 128 —
  4874 сборки, 418 мс. Порог теперь учитывает и свободные записи арен (их
  переиспользование до следующей сборки не растит кучу): 81 сборка, 27 мс.
  Тест порога обновлён под этот инвариант.
- `Task::new` при каждом создании задачи обходил планы всех функций программы
  ради размеров буферов; размеры считаются один раз (`execution::window`).
- SipHash в картах heap по handle (Atomic/Event/Lock/Group…) и в схеме строк
  заменён мультипликативным `HandleHasher`.
- `drive_task` уступал Tokio после каждого кванта в 4096 инструкций; каждый ход
  current-thread runtime опрашивает I/O-драйвер (`kevent`), и это было 52% времени
  главного потока. Кванты идут до 1 мс подряд, кооперативный бюджет Tokio по-прежнему
  принудительно отдаёт ход после 128 квантов. projection_only 13.7 → 8.8 мс.
- Вызовы native из JIT идут через heap call (`RunState.code`), без выхода
  в диспетчер; типизированный отказ откладывается в `Heap::deferred_raise`.

- Вход в JIT-регион загружает только live-in регистры PC (заметного эффекта нет).

### 2026-11-03 — диагностика простоя через Tokio

AsyncHost устанавливает on_thread_park: только когда сам Tokio исчерпал runnable
работу, проверяются внутренние ожидания каждого VM heap. Наличие внешнего таймера
исключает deadlock. Нет собственной очереди runnable задач, таймерного polling
или второго executor. Ошибка проходит обычный unwind с defer/destroy; перед этим
удаляется ожидающий native-запрос, чтобы cleanup не отдал permit брошенному waiter.

Проверены Event, rendezvous-канал и повторный захват Lock, включая defer и возврат
permit; реальный таймер не вызывает ложного deadlock. Проверен собственный и
внедрённый current-thread Tokio runtime. Для внедрения требуется установить
AsyncHost::check_stalled_tasks через Builder::on_thread_park; без hook обычный
Tokio не диагностирует невозможность будущего пробуждения.

Полный набор нового ядра: 166 PASS. CLI сообщает тот же смысл RuntimeError, что
origin; оформление общего префикса ошибок остаётся задачей совместимости
диагностик. Новые native I/O providers должны регистрировать внешний источник
пробуждения; сейчас из внешних ожиданий ядро поддерживает таймеры.
Следующий большой пункт фазы 6 — процессные workers и их native lifecycle.

### 2026-11-03 — semaphore/barrier и FutureScope

Tokio FIFO admission с бинарным разрешением и отдельным i64 счётчиком capacity:
это поддерживает i64::MAX без сужения к Tokio MAX_PERMITS. Очередь резервирует
capacity ещё до host poll; отмена немедленно снимает резерв. Permit.close ровно
один раз возвращает capacity, GC этого не делает. Lock продолжает использовать
прямой OwnedSemaphorePermit. Barrier использует Tokio watch с явным состоянием
поколения: cancellation/abort ломает его, reset отделяет новые ожидания от старых,
BarrierState — immutable snapshot. Channel и Barrier разделяют native request
контракт cancellation/tracing/wake без дополнительной wrapper allocation.

Origin/cold/JIT вернули 42 на semaphore FIFO/cancel/close/i64::MAX и barrier
cycles/indexes/abort/reset/cancel/snapshot/invalid-party-count. Отдельные unit tests
проверяют резервацию до poll, отмену старого поколения, native metadata GC.
Промежуточный permits() может различаться: origin возобновляет task внутри close,
Tokio — после передачи управления. Глобальный порядок планирования не гарантирован
актуальным [async guide](../../docs/async-guide.md#20-гарантии-и-сознательные-ограничения);
проверки FIFO ownership и счётчика после await точные. Историческое описание
immediate callbacks в compatibility.md не принимается за новое обещание scheduler.

FutureScope теперь исполняет action и ожидание группы плоским планом, кэширует
Future identity и дожидается дочернего cleanup при body failure/cancellation.
Комплексный fixture (string result, call count, ready/failing/cancelled body)
совпал с origin/cold/JIT; targeted regression добавлен. Общая async-фаза остаётся
открытой, включая completion streams, timeouts, workers, deadlocks и resource
retention для channel payloads (tracing GC сам по себе не реализует destroy ownership).

### 2026-11-03 — группы и структурированные комбинаторы

FutureGroup использует обычный плоский VM loop по уже запущенным Tokio tasks:
eager start, idempotent registration, sealing, active, cancellation, повторный wait,
наблюдение всех отказов и primary/secondary в порядке регистрации. AllFutures,
Raced и FirstSuccessful читают произвольный Sequencing через проверенные role
witnesses при старте тела, запускают все inputs и дожидаются cleanup после отмены.
Повторный вызов возвращает тот же Future; cache участвует в tracing GC, циклы
receiver→future→receiver не удерживаются после исчезновения внешних корней.
Первоначально готовые inputs рассматриваются в порядке входа, последующие — по
номеру завершения. Tokio watch будит selectors; polling по таймеру отсутствует.
Сканирование remaining inputs пока линейное на событие, а не готовая оптимальная
completion queue; не считать этот путь результатом performance gate.

На checkpoint до последних collector regression tests полный новый suite:
144 PASS; groups/collect targeted tests и отмена collector с cleanup — PASS.
Focused L08 теперь 23/23 выбранных run-кейса в cold/JIT (46 PASS).
Origin/cold/JIT совпали на group lifecycle, двух независимых group failures,
AllFutures order/duplicate/cache/empty, Raced winner и FirstSuccessful recovery,
а также отмене самого collector с завершением обоих cleanup.

**Открытое расхождение с origin:** explicit group cancellation скрывает отказ
Resource.destroy в origin (exit 42); новое ядро возвращает Cancelled с secondary
CleanupFailure (exit 1). Fixture `async-group-cancel-cleanup` сохраняет это различие.
Новое поведение следует текущему контракту std/async/scope и требованию роадмапа
не терять реальные cleanup failures; полная parity с origin не заявляется.
Общий async gate остаётся открытым: FutureScope, FutureCompletions, deadlines,
semaphore/barrier, workers, deadlock diagnostics и полный OCS ещё не закрыты.

### 2026-11-03 — каналы, scalar conformance и общая свёртка рекурсии

Новый runtime получил независимые Cancellation/Cancelling, Atomic и Channel.
Каналы поддерживают буферизацию, rendezvous при capacity=0, FIFO обеих сторон,
идемпотентное закрытие с дочитыванием буфера и немедленное удаление отменённых
ожидающих. Tokio watch отвечает за уведомления; очереди канала задают семантику
передачи, но не планируют исполнение Task. Endpoint aliases делят native state;
GC видит сообщения, payload ожидающих и завершённые результаты. Объекты остаются
компактными handles. Atomic сохраняет значение как borrowed GC edge, не принимает
его ресурсное владение. Ошибка CAS не публикует новое значение.

У origin обнаружено расхождение с prose std/async/atomic.ok: Atomic(1)==Atomic(1)
возвращает true (native state не участвует в структурном равенстве). Новое ядро
пока сохраняет это наблюдаемое поведение; изменение контракта не маскируется
оптимизацией. Для native stdio реализованы UTF-8 encode, stdout/stderr byte writes,
частичные записи/Interrupted/typed NativeFailure. Packed byte storage пока нет.

Свёртка чистой точной int-рекурсии теперь анализирует CFG, copies и parallel phi
moves после вызова, а не один фиксированный шаблон факториала. Поддержаны add/mul,
произвольная база и шаг, обычный receiver. Эффекты, handlers, resources и другие
операции на пути возврата исключены из доказательства. Реальный compiler fixture
с миллионом нехвостовых суммирующих вызовов выполняется с постоянной глубиной
продолжений в cold/JIT; отрицательный тест вычитания сохраняет обычные продолжения.
Пустые immutable containers с never-листьями могут расширять тип, builders — нет.

Focused OCS использует штатный judge и budgets, не собственные ожидания:
[core probes](new-runtime/core-ocs-probes.json) — 167 выбранных успешных run-кейсов
L02/L03/L04/L05/L07, 334 PASS в двух режимах; [async probes](new-runtime/async-ocs-probes.json)
— 20 из 23 выбранных L08 кейсов, 40 PASS и 6 UNSUPPORTED (groups/collect).
Это не полный OCS: omitted cases, test mode, fixtures, сервисы и прочие ограничения
перечислены в JSON. Канальный FIFO/cancel/close/rendezvous fixture вернул 42 на
origin/cold/JIT; unit tests проверяют GC, удаление очереди и close/drain.
Новый runtime пока не объявлен совместимым на 100%; benchmarks ещё не запускались.

### 2026-11-03 — events, locks и сохранение host-сессии

Добавлен проверяемый intrinsic loader: std Event и Lock/LockGuard опускаются
в короткие планы нового dispatcher, без обращения к старому runtime. Event —
Tokio watch latch; Lock — Tokio Semaphore с одним разрешением. Native acquire
регистрируется в FIFO сразу, сохраняется между poll, отмена удаляет запрос сразу.
Guard.close идемпотентно отдаёт разрешение. GC не подменяет close: забытый guard
не отпирает lock, как и в origin; native state освобождается вместе с объектом.

Compiler fixtures Event (два ожидающих, отмена одного, repeated set, initial ready)
и Lock (FIFO, отменённый средний запрос, repeated cancel/close, defer close)
вернули 42 на origin/cold/JIT. Отдельные tests проверяют native очередь до host poll,
GC событий и guards, неверные intrinsic layouts/signatures.

LocalSet теперь принадлежит Session, а startup acknowledgement хранится в Session.
Прерывание Rust host poll сохраняет дочерние кадры и корни; проверены остановка
на timer и остановка во время 20 000 ready-await eager startup, GC и возобновление.

Найдено и исправлено реальное расхождение: положительный timer на 1 ns нельзя
считать ready только потому, что deadline истёк. До доставки host это pending
promise; иначе терялась отмена и менялся primary/secondary cleanup failure.
Регрессионный fixture совпал с origin после исправления. Spawn startup использует
двустороннее acknowledgement, чтобы родитель продолжил до доставки уже истёкшего
таймера. На предыдущем полном checkpoint до locks: 124 tests PASS; последующие
lock/host-resume targeted tests PASS. Полный async conformance ещё не пройден.

### 2026-11-03 — local spawn и первое завершение дерева задач

`fut.spawn` запускает независимый Task через Tokio LocalSet. Startup acknowledgement
отправляется только при завершении или настоящем language Pending; fuel yield и
готовый await не дают родителю продолжить преждевременно. Проверены 2000 вложенных

выполняет cleanup. Root shutdown отменяет зарегистрированные pending tasks,
дожидается очистки, затем сообщает ненаблюдённый отказ через обычный Error.text.

действительно выполнен до возврата корня, а его отказ присоединён к Cancelled как

ArrayLookup поддерживает found/missing и fallback: parallel edge moves читают
старые регистры, найденное значение записывается после них. Анализ живых значений
учитывает определение результата только на found-ребре.

45 tests PASS (7 unit + 38 integration), Clippy нового crate (`--no-deps -D warnings`)
и dependency guard PASS. Проверены Unicode/UTF-8, пустой separator, slice errors
на огромных int, преобразования scalar→str, текстовые roots при GC,
builder aliases/finish, массивы и fallback с конфликтующими edge moves.
Фазы 2–4 остаются открыты: maps/enums/roles/closures/any, полный scalar-контракт,
cleanup/исключения/native/async и приёмка conformance ещё не выполнены.

### 2026-11-03 — late binding, successor и устранение локальных объектов

Реализованы obj.init и obj.next: позднее поле связывается один раз, изменения
видны прежним алиасам; successor создаёт новую идентичность и сохраняет исходные
поля/алиасы. Undef остаётся внутренним состоянием конструктора, а не null языка.
Перед вычислениями оба режима отвергают несвязанное значение, включая f64 SSA.
Введён консервативный local escape analysis: ObjNew с единственным определением
и только ObjGet-потребителями заменяется снимком полей в свежих типизированных
регистрах. Захват сохраняет исходные значения, даже если источники перезаписаны;
передача объекта в вызов, поздние связи и aliases исключают это преобразование.
Это ещё не межпроцедурный inlining и не полный escape analysis.

35 tests PASS (5 unit + 30 integration), Clippy PASS. Тест GC теперь специально
препятствует устранению объектов и требует не менее 7 выполненных сборок;
проверены nested object + bigint через suspended caller, циклы через obj.init,
повторное связывание, successor, снимки scalar replacement и unbound float.
Выбран и реализован базовый nonmoving mark/sweep allocator; отмечен соответствующий
подпункт. Фаза 3 целиком открыта: все классы корней, cleanup, равенство,
межпроцедурный анализ и оставшиеся контейнеры ещё требуют реализации/проверок.

### 2026-11-03 — scalar-типы и первые объекты на новом GC

Добавлены finite float (f64 SSA), byte/char, битовые операции, преобразования
чисел и точные rat. Малые дроби хранятся в слоте без аллокации, большие — через
num-rational. Сохранены десятичный контракт float→rat и DECIMAL128 для rat→float.
Собственная проверка SPB проверяет типы операндов и арность до JIT/оптимизации.
Числовые проверки: 28 tests PASS; найденное Clippy перекрытие шаблонов исправлено.

ObjNew/ObjGet работают в cold/JIT, через вызовы и приостановки. Заголовок
(descriptor ID) и поля размещены в одном boxed slice; ссылки — generational
handles. Общий heap трассирует объектные поля и числовые значения итеративно,
с повторно используемым worklist, без старых Region/Rc<Object>. Сборка nonmoving,
stop-the-world после фиксации инструкции; корни — живые регистры и сохранённые
caller-значения. Копирование handle не обходит граф. Объекты с destroy пока явно
отклоняются: сборщик памяти не подменяет языковой cleanup.

31 tests PASS (5 unit + 26 integration), включая цепочку 100 000 объектов,
сборку недостижимого цикла, повторное использование и stale handles, 1000
объектных аллокаций при живом вложенном объекте с большим int в caller.
Clippy нового crate и dependency guard PASS. Ещё не закрыты поздние связи,
successor/равенство, escape analysis, native/exception/async roots и полный ABI;
фазы 2–3 остаются открытыми. Отдельного performance-сравнения не проводилось.

### 2026-11-03 — точные целые и первое устранение рекуррентных вычислений

Новые слоты — 16 байт (payload/tag), малые int и bool хранятся непосредственно.
Большие int используют собственные generational handles и `num-bigint`;
старые Value/IntValue/runtime не подключены. Сложение/вычитание/умножение и
сравнение малых int выполняются в native SSA, переполнение и большие операнды
переходят в точный Rust-путь. Остаток сохраняет знак делимого, ноль даёт ошибку.
Числовой heap собирает мёртвые записи по живым активным регистрам и сохранённым
caller-значениям; поколение ссылки проверяется. Это ещё не полный объектный GC.

Полная чистая форма factorial с базой n<=1→1, шагом n-1 и умножением результата
распознаётся независимо от имени и преобразуется в цикл с аккумулятором.
Регистровые алиасы и отличающиеся формы не считаются эквивалентными автоматически.
Проверены отрицательная/нулевая база и результаты до 300! без продолжений вызовов.
Это первый доказанный шаблон, не преобразование любой рекурсии в O(1) памяти.

`cargo test -p sparrow-engine`: 18 tests PASS (2 unit + 16 integration).
Проверены границы i64, большие значения, нормализация, нулевой делитель,
приостановки, GC со значением в ожидающем caller и 5000 аллокаций при ограниченном
размере numeric heap. Clippy для нового crate (`--no-deps -D warnings`) PASS.
Float/rat/byte/char, остальные int-операции, typed failures и полный native ABI
остаются открытыми пунктами фазы 2 и последующих фаз.

### 2026-11-03 — прямые вызовы и плоская рекурсия scalar-подмножества

Новый dispatcher исполняет прямые вызовы без вложенного входа в Rust/JIT.
Call с непосредственным Return его результата заменяет текущую функцию;
взаимные хвостовые вызовы работают тем же способом. Обычный вызов сохраняет
метку возврата и только живые после вызова значения в общих буферах.
Одно активное окно регистров переиспользуется; аргументы захватываются до
перезаписи, полный кадр не обнуляется и отдельный Vec на вызов не создаётся.
Буферы нехвостовых продолжений растут амортизированно по необходимой глубине.

Проверки: 1 unit + 11 integration tests PASS, включая миллион взаимных хвостовых
вызовов в каждом режиме без роста продолжений; 10 000 нехвостовых продолжений
с одним сохранённым значением при 1000 регистрах функции; восстановление
вложенных возвратов и перестановку аргументов. Поддерживаются пока только
scalar-функции без handlers/cleanup. Общая хвостовая позиция, аккумуляторы,
точная арифметика, ошибки, объекты и async ещё не реализованы; фаза 2 открыта.

### 2026-11-03 — возобновляемое исполнение и анализ живых значений

В `sparrow-engine` добавлены собственные сессии и ABI `(RunState*) -> status`,
ограниченный бюджет исполнения, возврат и приостановка с сохранением PC.
Поддержаны bool, ветвления, циклы и параллельные присваивания на рёбрах CFG.
Backward dataflow определяет живые регистры с учётом циклов и перестановок;
JIT сохраняет на приостановке только живые значения. Cold/JIT возобновляются
из одного контракта состояния без Rust-рекурсии и без аллокаций на resume.
Область слотов пока резервируется для полного scalar-кадра; GC/async/calls
не реализованы и не считаются закрытыми этим механизмом.

Проверено 1 unit + 7 integration tests: оба режима, бюджеты 0/1/несколько/max,
перестановки регистров, повторное получение результата, живые значения и миллион
шагов бесконечного цикла с возвратом управления. Платформа проверки — macOS arm64;
JIT использует поддержанный Cranelift native target, отказ его построения — ошибка,
не переход в старое ядро. `--cold` явно выбирает новый cold executor.

### 2026-11-03 — первый исполняющий каркас

Добавлены crate `sparrow-engine` и бинарник `sparrow-next`: независимые loader,
проверенный план исполнения, native i64 SSA JIT и собственный cold path.
В bootstrap поддерживаются только const/move/return для синхронного int entry;
остальные инструкции и большие целые явно отклоняются, fallback отсутствует.
Это не готовая замена Sparrow. Контекст исключений/GC/async и полный ABI остаются
открытыми, поэтому фаза 1 целиком не закрыта.

Проверки: `cargo test -p sparrow-engine` — 4 integration tests PASS;
`python3 tools/check-sparrow-boundary.py` — три графа зависимостей PASS,
включая запрет старых runtime/VM/compiler/corosensei для нового ядра.
Код и ограничения: [sparrow-engine](../crates/sparrow-engine/README.md).
