# Архитектура okkama-rs

## Конвейер

```text
исходный текст (UTF-8)
  └─ source::SourceFile          текст + индекс строк
       └─ syntax::lexer::lex     Vec<Token> + лексическая диагностика
            └─ syntax::parser    ast::Program или первая синтаксическая ошибка
                 ├─ syntax::prune::strip_test_items   (необязательно)
                 └─ syntax::print                     tree / json
                 └─ syntax::prune::strip_test_items      (check, ir, build)
                      └─ analysis::analyze        registry + THIR тел, все ошибки
                           └─ lowering::lower_program / lower_linked
                                └─ ir::Module (OIR-1) → ir::verify

check: только анализ (`okkama check`, OCS-режим check) — все ошибки программы
build: ir::Module → codegen::generate → выбранный backend → Artifact → файлы (CLI)
будущие стадии: lowering из THIR, другие backend, jit
```

Точка входа — `syntax::parse(&SourceFile, &ParseOptions) -> Result<Program,
Vec<Diagnostic>>`. Если в файле есть лексические ошибки, возвращаются все они
и парсер не запускается: из лексически некорректного исходника программа не
строится, как и в `okkama-pl`. Иначе возвращается первая синтаксическая
ошибка.

## Крейты

- **okkama-compiler** — библиотека. Она не читает аргументы командной строки,
  не печатает в stdout/stderr, не завершает процесс и не зависит от CLI.
  Результаты и ошибки она возвращает значениями.
- **okkama-cli** — бинарник `okkama`. Он читает файл или stdin, проверяет
  UTF-8, разбирает опции, выбирает поток вывода и код выхода.

Модули библиотеки устроены так, чтобы любой из них позже можно было вынести в
отдельный крейт без переписывания: зависимости идут только «вниз» (`source` ←
`diagnostics` ← `syntax` ← будущие стадии), а циклов нет.

## Модули и решения

### `source`

`Span { start, end }` — полуоткрытый диапазон байтов UTF-8 (`u32`, то есть
файлы до 4 ГиБ; более длинный текст `SourceFile::new` отвергает). Байтовые
смещения дёшевы, однозначны и совместимы со срезами `&str`. Строки и столбцы
вычисляются только для вывода, по одному правилу для всего крейта:

- строки разделяет только LF, поэтому CRLF и LF нумеруются одинаково, а
  одиночный CR строку не начинает;
- нумерация с 1;
- столбец считается в Unicode scalar values, и табуляция занимает один
  столбец.

### `diagnostics`

`Diagnostic { kind: Lexical | Syntax, message, span, found }`. Поле `found`
— это токен (или конец ввода), на котором остановился парсер.
`render`/`headline` — чистые функции, возвращающие текст. Тексты синтаксических
ошибок совпадают с Perl-парсером слово в слово, поэтому реализации можно
сравнивать механически (см. [compatibility.md](compatibility.md)).

### `syntax::token` и `syntax::lexer`

Токен хранит вид, `Span` и, только у литералов, разобранное значение. Исходное
написание всегда доступно через `SourceFile::slice(span)`. Значения не
привязаны к машинным типам Rust:

- `IntLiteral { radix, digits }` хранит цифры строкой (без префикса и `_`);
  проверять, умещается ли десятичный литерал в `int`, — задача семантики;
- для `0x`/`0b` лексер сам проверяет предел `INT64_MAX`, потому что так
  записано в грамматике;
- `FloatLiteral { whole, fraction }` хранит обе части текстом;
- `StrLiteral { value, form }` различает формы `"..."`, ```` ```...``` ````
  и `endl`.

Лексер повторяет `Okkama::Lexer` токен в токен: longest match с одним
символом lookahead, `endl` как псевдоним `"\n"`, ASCII-идентификаторы,
отдельные токены для удалённых конструкций (`null`, `?.`, `**`, `isa`, ...).
Удалённые конструкции нужны, чтобы парсер объяснял ошибку, а не видел
обычный идентификатор.

Лексер не может зациклиться: каждая итерация потребляет хотя бы один символ,
а сканеры строк и комментариев останавливаются на конце ввода. После ошибки
он восстанавливается локально: дочитывает литерал до кавычки или пропускает
неверный символ. Поэтому одна ошибка даёт одно сообщение, а не каскад.

### `syntax::ast`

Типизированное дерево на `enum`/`struct`:

- `Program`, `Item`, объявления (`ObjectDecl`, `RoleDecl`, `ActionDecl`, ...);
- `Stmt`/`StmtKind` и `Block`;
- `Expr`/`ExprKind`;
- `TypeExpr`/`TypeKind`, `ResultSpec`, `ActionResult`.

У каждого узла есть `Span`, у каждого имени — `Name { text, span }`.

В дереве нет таблиц символов, разрешённых имён, вычисленных типов и
runtime-значений. Парсер ничего не «рассахаривает»: async, касты, проекции,
функциональные суффиксы, `endl`, `test`/`fake` остаются в том виде, в каком
записаны. Синтаксически значимые различия сохраняются: три формы
конструктора, секция `private:`, `if`/`match`/`try` как оператор и как
выражение, группировка скобками, форма строки.

### `syntax::parser`

Recursive descent: одна функция на продукцию грамматики, каждую можно читать
рядом с `docs/okkama-grammar-1.0.md` и `okkama-pl/lib/Okkama/Parser.pm`.

- `mod.rs` — состояние, курсор, имена, ошибки, заголовок модуля и импорты;
- `decl.rs` — элементы модуля, объекты, члены, роли, natives, caps, enum,
  test/fake;
- `stmt.rs` — блоки и операторы;
- `expr.rs` — выражения;
- `types.rs` — типы, `result_spec`, generic-параметры.

Решения:

- **Precedence climbing для бинарных операторов.** Грамматика записывает их
  лестницей из десяти уровней. Одна функция на уровень давала около тридцати
  стековых кадров на каждую скобку (47 КиБ на уровень вложенности в
  отладочной сборке). Поэтому бинарные операторы разбираются одной функцией
  по таблице приоритетов `binary_operator`; деревья получаются те же, и это
  подтверждено дифференциальным сравнением. Унарные, постфиксные и первичные
  формы — по одной функции.
- **Ограничение вложенности.** Каждая рекурсивная продукция проходит через
  `Parser::nested`. При превышении `ParseOptions::max_nesting` (по умолчанию
  64) выдаётся диагностика, а не переполнение стека. В корпусе максимальная
  вложенность равна 20. При пределе 64 самые «тяжёлые» формы помещаются в стек
  потока 2 МиБ даже в отладочной сборке; это проверяет
  `tests/parser_robustness.rs`.
- **Конец ввода.** Цикл верхнего уровня идёт до `EOF`, поэтому корректный
  префикс с мусором после него — ошибка.
- **Закрывающие `>` generic-аргументов.** `>>`, `>>>` и `>=` лексер выдаёт
  целыми токенами. Когда парсер типа ждёт `>`, `consume` разрезает составной
  токен на месте. Так разбираются `Box<Box<int>>` и `let x is Box<int>= ...`,
  а в выражениях `>>` остаётся сдвигом.
- **Контекстные имена.** `is_name_token` пропускает любые словоподобные
  токены, кроме удалённых конструкций. Поэтому `test.ok()`, `value.last()`,
  метка действия `is(...)` и сегмент `module test/more` разбираются.
  Объявления переменных, полей, параметров и типов требуют настоящий
  идентификатор (`consume_identifier`, `consume_type_name`, ...).
- **Контекстно-зависимые ограничения**, которые Perl-парсер проверяет как
  синтаксические, проверяются и здесь, чтобы решения «принять/отвергнуть»
  совпадали. Примеры: только `main()` на уровне модуля, место variadic,
  дубликаты generic-параметров, `with_*`, `spawn` без вызова. Всё, что требует
  имён или типов, оставлено анализу.

### Режимы test/fake и `syntax::prune`

`ParseMode::Full` разбирает тела `test` и `fake`. `ParseMode::Production`
делает это так, как требует спецификация (§14): тела проходят как
сбалансированные скобки и записываются в дерево как `TestBody::Skipped(span)`
и `FakeBody::Skipped(span)`. Сам парсер узлы не удаляет. Удаление —
отдельный явный проход `prune::strip_test_items`, покрытый тестами.

### `syntax::print`

Оба формата строятся из одного нейтрального описания дерева `print::Node`
(вид, span, подписанные поля), которое создаёт `print/build.rs`. Функции
построения сопоставляют каждый тип AST исчерпывающе, без `_`. Поэтому
новый вариант AST, не известный принтерам, — ошибка компиляции, а `tree` и
`json` не могут расходиться в содержании. JSON пишется вручную (без
зависимостей), детерминированно, с экранированием управляющих символов.

### `analysis`

Семантический анализ проверяет всё, что решается до исполнения, и не зависит
от того, что умеет backend: программа с ошибкой типа получает её, даже если
рядом есть конструкция, которую lowering ещё не поддерживает.

- `registry` — таблица объявлений всех модулей программы. Три прохода: имена
  (объекты, роли, enum, `native`, `native object`, caps — включая внешние
  `cap Owner::Name`), импорты (`take`, `as`, пространства имён по последнему
  сегменту пути), сигнатуры (поля, конструкторы, actions, `does`,
  ограничения generic-параметров). Проверки объявлений — тексты
  Perl-анализатора. Системные `Error`, `NativeFailure`, `Cancelled` видны без
  импорта; стандартные роли (`compare.Comparing`, `collections/iteration`
  `Iterating`/`Cursor`, `collections/sequence.Sequencing`, `size.Sizing`,
  `io/stream` `ByteSource`/`Writing`) узнаются по модулю и дают builtin
  значениям номинальные адаптеры.
- `ty` — семантические типы. Generic-объявление одно: `Box<T>` и `Box<int>` —
  `Object(Box, [Param T])` и `Object(Box, [Int])`.
- `check` — проверка тел. `Checker` обходит тело и строит THIR; ошибка
  сообщается один раз и превращает значение в `Ty::Error`, на котором
  дальнейшие проверки молчат, поэтому находятся все независимые ошибки.
  Тела generic-объявлений проверяются один раз, символьно: параметр типа
  непрозрачен и доступен только через роль-ограничение.
- `thir` — типизированное дерево: разрешённые локальные (`LocalId`), поля,
  выбранные перегрузки и конструкторы, специализации generic, операторы по
  типам операндов, явные узлы границ (`Coercion`: `Take`, `RoleWrap`,
  `RoleNarrow`, `Retag`, `Box`) и приведений (`Cast`).

Правила, которые анализ применяет:

- типы и приведения: разные числовые категории без явного каста не
  смешиваются (R02, D-046); `byte` — не ключ словаря (D-007);
- ожидаемый тип границы (`let x is T`, поле, параметр с однозначной
  сигнатурой, результат действия) проходит в ветви `if`/`match`/`try`,
  значения `last`, элементы литералов и аргументы generic-конструирования
  (§6.5); разнородный литерал без цели — `@any` (R08);
- перегрузки выбираются по специфичности (§11.8): точный тип > роль > `any`;
- роль → роль только сужением (§12.1); массив пересекает границу
  `Sequencing<E>`/`Iterating<E>`, если его элементы пересекают `E`;
- `for` и функциональные операции обходят массивы, диапазоны, словари
  (только функциональные) и `Iterating<T>`, в том числе ссылку роли, чьи
  действия включают `cursor() is Cursor<T>`; `for` в позиции значения даёт
  значение последней итерации или `last value` (§9.10).

- `flow` — проверки потока по THIR после типизации: обязательство successor
  (§11.1: алиасы делят обязательство, погашение — узлы `Take`, слияние —
  «непогашено, если непогашено хоть на одном пути», тело цикла может не
  выполниться, `defer` засчитывается при выходе своей области, `throw`/`panic`
  вправе бросить обязательства) и инициализация полей конструктора (поле, не
  связанное ни на одном пути к концу, — ошибка; не на всех — проверка во время
  исполнения; чтение до связывания; связывание в цикле до связывания до него).

### `ir` и `lowering`

`ir` — модель OIR-1 (`docs/compiler/OIR-1.md`): типизированный SSA с
параметрами блоков. `Module` хранит имя, версию, неразрешённые импорты,
объявления объектов (поля в порядке объявления, ссылки на функции default),
функции и точку входа. `Function` — символ, параметры, результат, атрибуты
владельца (`entry`, `method C`, `ctor C`, `successor C`, `default C.f`,
`private`), таблица типов значений и блоки. Блок 0 — вход; каждый блок имеет
параметры, инструкции и ровно один терминатор.

- `ir::cfg` — места определений, преемники и доминаторы (Cooper–Harvey–Kennedy);
  общие для верификатора и JVM backend.
- `ir::verify` — правила §17: однократное определение, доминирование
  использований, типы инструкций и аргументов переходов, достижимость блоков,
  авторитет `obj.*`/`private`, обязательство `^C` (на каждом нормальном пути до
  `ret` — `succ.take`, возврат или передача параметру блока), линейность
  сборщиков по путям (ни одно использование не достижимо из другого до
  переопределения).
- `Display` у `Module` — канонический текст §18 (`^bN`, `%N`).

`lowering::lower_program` переводит проверенную программу (`analysis::Analysis`)
в OIR механически: правил языка он не проверяет. `ctx` строит объявления OIR:
каждая специализация generic-объявления (`Box<int>`) — отдельный объект со
своими функциями, специализации создаются при первом упоминании типа;
функции выделяются заранее (natives, затем по модулям defaults, `destroy`,
конструкторы и actions в порядке исходника), shorthand-конструктор с неполным
набором полей специализируется по форме вызова (`@C.new#k.a.b`) при первой
встрече. `body` переводит THIR-тело в блоки:

- `FnBuilder` пишет блоки в любом порядке; `finish` удаляет недостижимые блоки
  (код после `return`, ветви литеральных условий) и перенумеровывает блоки в
  reverse postorder, а значения — по порядку определения;
- изменяемые переменные (rebind локальных successor-типов, поля строящегося
  объекта, staged-поля successor) — текущие SSA-значения; ветви и выходы циклов
  собираются как отложенные плечи и сводятся одним `join`, различающиеся
  значения становятся параметрами блока, присваиваемые в цикле — параметрами
  заголовка;
- must-use: узел THIR `Take` даёт `succ.take`; на слиянии ветвей и на входе в
  цикл значение `^C` гасится в каждой ветви (обязательства уже проверил
  `analysis::flow`), поэтому параметр слияния — `C`; литеральные
  `if true`/`if false` известны заранее, мёртвая ветвь не выпускается;
- роли: системная `Error` создаётся при первом упоминании; узлы границ THIR
  (`RoleWrap`, `RoleNarrow`, `Retag`) — `role.wrap`, `role.narrow`,
  `array.retag`/`map.retag`; вызов через роль — `call.role`; операнды вызова
  вычисляются слева направо, затем границы параметров по порядку;
- `try`/`catch`: тело и handlers — области отказа (`TryCtx`); `FnBuilder`
  назначает блоку цель unwind при первой инструкции, а присваивание
  переменной, которую получает dispatch, начинает новый блок. Dispatch
  выбирает catch по порядку, тело catch получает свой блок причин
  (`fail.caused`), несовпавший отказ уходит дальше через `raise`;
- коллекции (`body/collections.rs`): `for`, `map`/`filter`/`reduce` над
  массивами и диапазонами — счётный цикл с индексом и состоянием в параметрах
  заголовка; `map`/`filter`, спред диапазонов в литералах и `@int(...)`/
  `@string(...)` строят массив линейным `builder`; тип результата `map`
  задан в THIR; `xs[i] else` —
  `array.lookup` и `join`; `first()`/`last()` — `array.lookup` и `trap empty`;
  builtin-действия массивов, строк, `int` и `bool` — отдельные инструкции с
  текстами ошибок Perl;
- `byte` и `char`: литерал `'x'` — `const`, `byte(200)` — `const 200: byte`,
  иначе `byte.from` с проверкой диапазона; арифметика двух `byte` и унарный
  `-` расширяются `cvt byte→int` (смешение с `int`/`float` — ошибка, R02), битовые операции и сравнения двух `byte` — `byte.*`,
  равенство `char` — `char.eq`/`char.ne`; битовые действия `int`/`byte`
  (`bit_count`, `rotate_left`, …) — инструкция `Bits`;
- владение и `defer` (`body/scopes.rs`): если в модуле есть `destroy`,
  каждая блочная область и корень функции получают регион
  (`region.enter`/`leave`/`unwind`); plain-типы (`ModuleCtx::is_plain`,
  неподвижная точка по объектам и ролям) регионов не касаются. Результат
  вызова — `region.track` текущей области, `let`/rebind/поля строящегося
  объекта — `region.adopt` своей области, параметры и `self` — `adopt`
  корня, пойманный Error — `adopt` тела `catch`. Цель отказа области —
  цепочка `F_n … F_0` в одном слоте стека `tries` (как у `try`); выходы
  (`ret`, конец блока, `next`/`last`) исполняют defer в обратном порядке и
  `region.leave … keep payload`; значение ветви `if`/`match`/`try`
  переходит во внешнюю область;
- enum и `match` (`function/matching.rs`): `Light.red` — `enum.case`, если
  имя не перекрыто локальной привязкой; `==` двух значений одного enum —
  `enum.eq`; `match` — цепочка `cond` с ленивыми образцами через
  `binary_values` (общий `==`), при полном покрытии enum или `bool` без
  `else` последний `case` не проверяется;
- словари (`function/maps.rs`): литерал `[k: v]` — `map.new` (повтор ключа —
  последнее значение), `m[k]` — `map.get`, `m[k] else` — `map.lookup` и
  `join`; `size`/`has`/`keys`/`values` — `map.*`; обход пар — счётный цикл по
  `map.keys`/`map.values`, `filter` собирает `mbuilder`; `[]` и `[:]` в
  ветвях получают тип типизированной ветви (`retag`).

Generics (`decls::instantiate`, `function/generics.rs`): generic-объекты и
роли регистрируются шаблонами (`TemplateInfo`), экземпляр создаётся по
`resolve_type` (`Box<int>`) или выводом при конструировании и собирается
обычным `collect_object`/`collect_does`/`collect_role` под подстановкой
`type_env`; задачи lowering экземпляра получают ту же подстановку.

Модули (`lowering/modules.rs`): `lower_linked` (один файл) и
`lower_linked_files` (файлы одного модуля, §5.1) загружают импорты через
`ModuleLoader` (CLI — `FileLoader`: `OKKAMA_IMPORT_DIRS`, каталог
импортирующего файла, `OKKAMA_STDLIB_DIR`), обходят граф в глубину
(зависимости первыми, цикл — ошибка) и передают анализу `SourceModule`
каждого файла: зависимости, затем файлы корня. Реестр (`Registry`) держит
для каждого модуля свои объявления (`own`) и видимые имена (`scope`: свои,
взятые `take`, у файлов корня — ещё и объявления соседних файлов).
Объявления импортированных модулей получают префикс `io.stdout::`,
объявления корня — без префикса. `native`-действия — функции
`[extern "модуль::имя"]`. Ошибка в файле (`LinkError::Lowering { source }`,
`CheckError { source }`) печатается с его именем.

`LoweringError::Unsupported` — корректная Okkama, которую IR ещё не выражает;
`LoweringError::Invalid` — нарушение правила языка (CLI печатает
`semantic error`). Lowering проверяет свой результат верификатором. CLI перед
lowering удаляет test/fake-объявления явным проходом `prune`.

### `codegen`

```text

  jar.rs             Artifact::jar: исполняемый JAR (ZIP + DEFLATE, манифест Main-Class)
  jvm/mod.rs         раскладка классов и дескрипторов, generate
  jvm/outline.rs     деление больших функций: разрез длинных блоков, вынос замкнутых областей
  jvm/function.rs    тело функции: инструкции, терминаторы, кадры, unwind
  jvm/classes.rs     классы объектов (поля, <init>, equals/hashCode, мосты) и интерфейсы ролей
  jvm/runtime.rs     constant pool главного класса, вызовы okkama.rt, launcher
  jvm/asm.rs         ассемблер байткода: метки, глубина стека, StackMapTable
```

Class-файлы рантайма хранятся в репозитории, поэтому сборке `okkama-rs` JDK
не нужен. После изменения `runtime/jvm/src*` их пересобирает
`tools/jvm-runtime/build.sh` (`javac --release 8` и `--release 22`).
`build.rs` встраивает все файлы `classes/okkama/rt` и строит таблицу natives:
провайдер native `runtime/<модуль>::<имя>` — публичный статический метод
`runtime_<модуль>__<имя>` любого класса рантайма; дескриптор сверяется с
сигнатурой native при генерации.

Backend получает весь `ir::Module` и возвращает `Artifact`: основной файл
первым, затем вспомогательные. Внутри него нет CLI, повторного парсинга или
файлового ввода-вывода. `-o X.jar` — CLI пишет один исполняемый JAR
(`Artifact::jar`); `-o X.class` — основной файл по пути `-o`, остальные рядом
под их относительными именами (`okkama/rt/Rt.class` — в подкаталоге). Запись —
только после успешной генерации: ошибка backend сохраняет предыдущий артефакт.
`generate` сначала вызывает верификатор, затем `outline::split_large`.
`okkama run` кэширует классы во временном каталоге по хешу и запускает `java`
(exec).

JVM backend (§21.4 спецификации):

- функции — статические методы главного класса; `main` — `okkamaMain`,
  символ `Purse.total#1` — метод `Purse$total$1`;
- объект — `final` класс `<Главный>$<Объект>` с `final`-полями в порядке
  объявления и конструктором, принимающим все поля;
- `int` — `java.math.BigInteger` (точная арифметика), `bool` — `int` 0/1,
  `str` — `String`, `C` и `^C` — ссылка на класс объекта, массив и сборщик —
  `java.util.List` (`ArrayList`, `bool` в элементах — `Boolean`; сборщик линеен
  и дописывается на месте, `builder.finish` — та же ссылка);
- объект наследует `okkama.rt.Obj` (владелец, порядок создания); `refs`
  отдаёт поля, через которые достижимы идентичности, `destroyBody` вызывает
  функцию `destroy`; регион — `okkama.rt.Region` (`adopt`, `track`, `leave`,
  `unwind`: обратный порядок регистрации, каждая идентичность — один раз,
  отказы destroy — основной/вторичные); launcher печатает вторичные отказы
  как Perl (`Secondary cleanup failure:`);
- `float` — `java.lang.Double` (одна ссылка на слот, как у прочих значений),
  операции и текст — `okkama.rt.Floats` (кратчайшее представление через
  `BigDecimal`, правило Go для экспоненты);
- `rat` — `okkama.rt.Rat`: несократимая дробь из двух `BigInteger`
  (знаменатель > 0), текст `n/d`, ошибки — тексты Perl;
- enum — класс `<Главный>$<Enum>` со `static final` полями `okkama.rt.Case`
  (создаются в `<clinit>`), `enum.case` — `getstatic`, `enum.eq` — разность
  номеров;
- `byte` и `char` — JVM `int` (дескриптор `I`), в коллекциях — `Byte` и
  `Integer`; сравнения двух `byte`/`char` — `isub` и `Integer.signum`;
- словарь и `mbuilder` — `java.util.Map` (`TreeMap` с компаратором
  `okkama.rt.KeyOrder`: строки по code points), ключи и значения `bool` —
  `Boolean`;
- `val.eq` — `Objects.equals`: классы объектов сравнивают поля в порядке
  объявления, списки — поэлементно, словари — по парам;
- каждое SSA-значение — свой local slot; параметры блоков заполняются на рёбрах
  через стек (параллельное присваивание); перед каждым блоком кроме входа —
  `full_frame` из значений, доминирующих над блоком, и его параметров;
- сравнения `int` вычисляются без ветвлений из `compareTo` (−1/0/1);
- роль — интерфейс `<Главный>$<Роль>`, объект реализует его мостовыми
  методами экземпляра, вызывающими статическую реализацию; `call.role` —
  `invokeinterface`, `role.wrap` — тот же объект;
- системная роль `Error` — интерфейс рантайма `okkama.rt.Error`;
- отказ — `okkama.rt.Failure extends RuntimeException` (вид, Error-объект,
  изменяемая причина, без stack trace); цель unwind блока — запись exception
  table на байткод блока и заглушка, раскладывающая аргументы по параметрам
  цели; `catch` проверяет вид и `instanceof`;
- проверки и операции (`%` со знаком делимого, слово signed-64 и счётчик сдвига,
  индексы и срезы, диапазоны, строки по code points, `trim` по Unicode
  White_Space, `chomp` — CRLF или LF) — статические методы `okkama.rt.Rt`; Java `main(String[])` вызывает
  `Rt.exit`/`Rt.report`: отказ печатается как в Perl (`RuntimeError: …`,
  `Panic: …`, `<Тип>: <text()>`) с кодом 1, результат `main` вне `0..255`
  отвергается.

Conformance: `okkama --ocs-capabilities` и `okkama --ocs-request R
--ocs-response P` (`okkama-cli/src/ocs.rs`) реализуют протокол
`ocs-adapter/1`: `parse`, `check` и `run` (сборка во временный каталог и
`java`; отказ программы launcher записывает в файл `OKKAMA_FAILURE_REPORT`).

Async: функция `[async]` — метод `name$body` и заглушка `Future.cold`;
`okkama.rt.Scheduler` исполняет задачи на потоках с одной эстафетой (порядок
обратных вызовов Perl), внешние операции (сеть, процессы, таймеры, SQLite) —
`Scheduler.offload` на рабочих потоках с доставкой исхода событием цикла.
Intrinsics std `async/*` — `okkama.rt.Intrinsics` (состояние в `Obj.intrinsic`).
`worker.spawn` — дочерняя JVM той же программы (`okkama.rt.Worker`,
`OKKAMA_SPAWN_WORKER`).

Большие функции (сгенерированные данные std, длинные литералы) делит
`outline`: длинный блок режется на цепочку `br`-блоков там, где живо не больше
32 значений, затем замкнутые доминаторные области выносятся в функции
`<символ>$part<N>` над живыми на входе значениями. Литерал длиннее 64
элементов lowering собирает потоково (`builder`). Предел остаётся у пула
констант класса.

`classfile` пишет big-endian заголовок, constant pool, поля и атрибуты `Code`
со StackMapTable и exception table. Записи `Long` занимают два индекса, строки
кодируются modified UTF-8 поверх UTF-16. Проверяются ограничения `u16`, длины
bytecode и 16-битные смещения переходов; переполнение формата возвращает
`CodegenError::InvalidInput`, а не усечённый индекс.

`analysis` и `jit` содержат документацию об ответственности и границах.
Общая схема дальнейшего развития:

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `analysis` | сборка модулей и импортов, разрешение имён, проверки объявлений, типы, факты потока управления | `source`, `diagnostics`, `syntax` |
| `ir` | структуры промежуточных представлений | `source` |
| `lowering` | AST → IR; далее — вход из анализа, рассахаривание и IR-проходы | `syntax`, `ir` |
| `codegen` | IR → артефакт выбранного backend (`.class`, объектный код и другие форматы) | `ir` |
| `jit` | IR → исполняемая память | `ir`, будущий рантайм |

AST остаётся неизменяемым и свободным от семантики: результаты анализа будут
храниться в отдельных таблицах, ключом в которых служит узел.

## Как добавить…

### …токен

1. Добавить вариант в `TokenKind` (`syntax/token.rs`). Указать его имя в
   `TokenKind::name` (имя из Perl `TokenType`, если токен там есть). Если это
   ключевое слово — добавить его в `TokenKind::keyword`, а если удалённое
   слово — ещё и в `is_reserved`.
2. Распознать токен в `Lexer::scan_token` (`syntax/lexer/mod.rs`) с учётом
   longest match.
3. Добавить тест в `syntax/lexer/tests.rs`: вид, лексема, пересечения с
   соседними операторами.

### …AST-узел

1. Добавить вариант или структуру в `syntax/ast/` (`mod.rs` — объявления,
   `stmt.rs`, `expr.rs`, `types.rs`) со `span`.
2. Компилятор укажет все `match` без нового варианта; первым делом это
   `print/build.rs` — описать там узел (вид и поля).
3. Добавить вид в `ALL_KINDS` (`tests/printer.rs`) и конструкцию в
   `tests/fixtures/all-syntax.ok`, затем обновить снапшоты
   (`OKKAMA_UPDATE_SNAPSHOTS=1`) и просмотреть diff.
4. Если узел виден в Perl-AST, добавить его в нормализаторы
   `tools/differential/differential.py` (`r_*` и `p_*`).

### …правило парсинга

1. Найти продукцию в `docs/okkama-grammar-1.0.md` и соответствующий метод в
   `okkama-pl/lib/Okkama/Parser.pm`.
2. Реализовать функцию в нужном файле `syntax/parser/`. Рекурсивные формы
   должны проходить через `nested`. Тексты ошибок — как в Perl, если там
   правило уже есть.
3. Добавить строку в [syntax-coverage.md](syntax-coverage.md).

### Как тестировать новую конструкцию

1. Положительный и отрицательные тесты в подходящем
   `tests/parser_*.rs`. Хелпер `common::expr_sexpr`/`body_sexpr` даёт
   компактную форму `(+ 1 (* 2 3))`, а `assert_rejects` проверяет текст
   ошибки.
2. Если конструкция рекурсивна, добавить её форму в `SHAPES` в
   `tests/parser_robustness.rs`.
3. Узел и снапшоты, как описано выше.
4. Дифференциальное сравнение:
   `python3 tools/differential/differential.py cases my-cases.json`, где
   `my-cases.json` — это `[{"id": "...", "source": "module app v1.0.0; ..."}]`.
   Расхождение с Perl либо исправить, либо, если поведение выбрано
   намеренно, описать в `tools/differential/known-divergences.json` и в
   [compatibility.md](compatibility.md) с основанием.
5. `cargo test --workspace` и корпусная проверка.
