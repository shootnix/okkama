# Перестройка ядра Sparrow

Статус: план, согласован пользователем 2026-11-06. Основание —
[разведка ядра](core-spike.md): прототип `crates/sparrow-proto` под клеткой
быстрее текущего `sparrow-engine` в 23–40 раз и sparrow-origin в 9–15 раз,
на массовых спаунах — на порядки.

## Целевая модель

1. **Синхронные функции** компилируются целиком (Cranelift) и вызывают друг
   друга прямыми машинными вызовами на нативном стеке. Роли — таблица
   `[роль, слот][дескриптор]` и косвенный вызов; замыкания — косвенный вызов.
2. **Async-функции** — возобновляемые машины состояний. Кадр — объект кучи и
   одновременно Future. `await` готового — результат; холодного — запуск тела
   тут же; иначе — сохранить регистры, записаться ожидающим, уступить.
   `spawn` стартует немедленно. Планировщик и всё внешнее ожидание — на Tokio.
3. **Значения без тегов там, где тип статический.** Тег остаётся у `int`
   (малое / BigInt), `any`, `rat` и незаполненных полей.
4. **Объекты — указатели на `[заголовок, поля…]`**, поле читается по смещению
   в машинном коде, аллокация — инлайн.
5. **Точный GC.** Корни: stack maps Cranelift (проход по frame records), кадры
   async в куче, корни Rust-стороны через посетителей. GC запускается только
   в точках безопасности машинного кода и диспетчера, никогда внутри native.
6. **Вытеснения внутри синхронного кода нет** (уступка — только на `await`).
   На обратных переходах циклов — проверка флага прерывания: отмена задачи,
   таймаут теста и завершение процесса останавливают зависший цикл
   типизированной ошибкой, а не вытеснением.

## Что сохраняется

- Загрузчик, верификатор SPB, построение плана (`Op`), анализ живых значений,
  проверка ролей и сигнатур — вход нового JIT.
- Natives (~17 тыс. строк, включая SQLite) — через сохранённый API `Heap`
  (`text`, `elements`, `allocate_*`, `object_get`, handles). Меняется реализация
  API, не провайдеры.
- Async-хост на Tokio, `native_io` Request, семантика отмены, cleanup,
  `destroy`, ошибок и трасс.
- Тесты: все семантические проверки (программа → результат, вывод, ошибка).

## Что переписывается

- `execution.rs` (плоский диспетчер, continuations, saved), `jit.rs`
  (регионы, heap calls), `value.rs`/`arena.rs` (handles с поколениями, `Box`
  на объект), синтезированные cold-планы intrinsic (становятся обычными
  функциями ядра или прямыми вызовами Rust).
- Тесты внутренних свойств плоской модели (14 наборов используют
  `resume(1)`, `continuation_depth`, `saved_value_count`): переписать на свойства
  новой модели или удалить, если свойство исчезло.

## Решения (подтверждены пользователем 2026-11-06)

- **R1. GC без перемещения на первом этапе.** Mark-sweep с классами размеров,
  аллокация инлайн из свободных блоков. Natives держат значения в локальных
  переменных Rust между аллокациями, runtime-объекты (Atomic, Event, Lock,
  Channel…) сейчас ищутся в картах по адресу объекта — перемещение сломало бы
  и то и другое. Перемещающий nursery — отдельная оптимизация позже, когда
  идентичность вынесена в заголовок, а natives переведены на корни-области.
- **R2. Глубокая рекурсия — большой стек потока VM** (резерв 1 ГБ виртуальной
  памяти, физическая — по мере роста) вместо отката в интерпретатор. Исчерпание —
  типизированная ошибка переполнения стека, как сейчас ограничение памяти.
- **R3. Без cold-интерпретатора.** Один режим исполнения; функции
  компилируются лениво при первом вызове (заглушка вызова). `Mode::Cold`
  в тестах исчезает; дифференциальная проверка — против sparrow-origin
  и IR-интерпретатора на conformance.
- **R4. Новый crate `sparrow-core`**, а не правка `sparrow-engine` на месте:
  текущий движок работает до паритета, natives и тесты переносятся в новый
  crate по этапам, после паритета `sparrow-engine` удаляется. CLI `sparrow-next`
  переключается на новое ядро в конце этапа 4.

### Этап 3. Async — проект (2026-11-06)

Семантика переносится из `sparrow-engine` (`future.rs`, `execution.rs`
`await_future`/`unwind`/`take_cancellation`, `async_host.rs`
`drive_task`/`shutdown_tasks`); все прогоны — под `caged.py`.

**Кадр async-функции = её Future** (объект кучи `FRAME`), слова:
`[header, state, result, failure, waiter, awaiting, resume, flags, registers…]`.
state: COLD / RUNNING / DONE / FAILED (позже — внешние: timer, I/O, event…).
`failure` — ссылка (отдельно от `result`, чей вид задан типом результата).
`waiter` — 0, кадр или payload-список ожидающих (повторный await из разных
задач). `awaiting` — Future, которого ждёт этот кадр (цепочка до самого
внутреннего ожидающего кадра задачи — для доставки отмены). flags: spawned,
observed, cancel_requested, cancel_delivered.

**3a. Ядро:**
- тело async-функции компилируется как `(ctx, frame) -> 0 | 1` (готово /
  pending); вход по `resume`: 0 — старт с параметрами из кадра, `pc + 1` —
  повторный вход в `await` после загрузки всех регистров из кадра;
- вызов async-функции выделяет холодный кадр (`rt_future_new`);
- `await` → `rt_await(ctx, self, future)`: DONE — значение; FAILED — поднять
  отказ (observed); COLD — запустить тело тут же (Rust вызывает машинный код);
  иначе — записаться ожидающим, сохранить регистры, вернуть pending;
- неперехваченный отказ тела: вызывающий тело (await/планировщик) видит
  `status = FAILED` после возврата, переводит Future в FAILED, сбрасывает
  статус и будит ожидающих;
- `fut.spawn` — немедленный старт: тело работает до завершения или первой
  приостановки; отказ ребёнка остаётся в его Future, родитель продолжает;
- `fut` done/cancelled/cancel; отмена COLD — FAILED(Cancelled); RUNNING —
  флаг; доставка: самый внутренний ожидающий кадр задачи возобновляется,
  его `await` поднимает Cancelled, раскрутка выполняет обработчики и cleanup;
- `FailureKind::Cancelled` (catch: встроенный объект `Cancelled`, роль Error;
  текст «Cancelled: Operation was cancelled»);
- планировщик: очередь готовых; async `main`; по завершении корня — отмена
  ещё работающих порождённых задач, ожидание их завершения, затем отказ
  неотслеженной порождённой задачи становится итоговым (как в старом движке).

**3a выполнен 2026-11-06** (`tasks.rs`, JIT: вход async-тела по `resume`,
`await` с сохранением регистров, `rt_future_new`/`rt_await`/`rt_complete`/
`rt_spawn`/`rt_fut`; async-реализации ролей, `call.cap` и замыканий дают
холодный Future). Проверки под клеткой: прототип `asyncs` (131 тыс. спаунов,
100 тыс. await) — результат верен, ~0.33 с против ~10.5 с у origin; 10-app —
вывод совпадает, ~0.50 с против ~0.93 с; L08 — 12 кейсов совпадают, 0
расхождений, 14 ждут intrinsics. Ошибка по пути: заголовок кадра хранил
`objects.len() + функция`, а GC брал раскладку по индексу функции — сборка
читала чужую раскладку (segfault после первой сборки); исправлено.

**3b.** Таймеры (`sleep`) через Tokio; intrinsics Atomic, Event, Lock,

**3b выполнен 2026-11-06.** Модель: async-intrinsic и async-native — тоже
кадр-Future (холодный при вызове, как любая async-функция), но его «тело» —
Rust-драйвер (`drivers.rs`), а не машинный код; у кадра драйвера после
регистров одно трассируемое слово состояния (payload для групп, коллекций,
таймаутов). Ждущий драйвер помечается PARKED: на ресурсе (событие,
блокировка, барьер, канал, таймер) или на нескольких Future сразу
(`listen`); пробуждение — только через `wake`, повторно в очередь кадр не
попадает. Отмена, дошедшая до припаркованного драйвера, будит его с
DELIVER_NOW, и драйвер сам снимает заявку (из очереди блокировки, канала,
барьера, таймеров); у драйвера, чья заявка уже исполнена (выдана
блокировка, передано значение), отмена остаётся запрошенной до следующего
`await`. Очереди ресурсов пропускают кадры, которые уже не PARKED.
Состояние примитивов (`primitives.rs`) — в таблице по адресу владеющего
объекта; объект наблюдается кучей, состояние уходит вместе с ним; ждущие
кадры и хранимые значения — корни. Порядок завершения Future — в старших
битах flags (для Raced/FirstSuccessful/Before/Within). Синхронные
intrinsics разрешаются по имени один раз при загрузке; для вызова
native/intrinsic через таблицу кода (роль, замыкание) компилируется
трамплин. Таймеры пока ждёт сам планировщик (`thread::sleep` до ближайшего
срока, когда очередь пуста); Tokio придёт с I/O-natives (этап 4).

Проверки (все прогоны — под `caged.py`): L08 — 25 совпадают, 0 расхождений,
1 ждёт natives (`db.query-lifetime`); L01–L07 — 293 / 0 (было 287: прошли
кейсы с intrinsics через роль); L09/L12 — 22 / 0, остальные 31 ждут
natives. Пробы против origin, вывод совпадает: 300 задач на одной Lock со
сном внутри (счётчик 300), канал на 100 тыс. сообщений при ёмкости 0/1/16
(origin 0.84 с, core 0.34 с), отмена спящей 30 с задачи и выход с ещё
спящей задачей (мгновенно), Semaphore(4) на 100 задач (пик 4), Raced и
AllFutures на таймерах.

`FutureCompletions` (тоже 3b): прямой вызов `completion()` читает origins
сразу, как старый движок (JIT вызывает для него intrinsic, а не создаёт
холодный кадр); через роль или замыкание — при первом запуске драйвера.
Запросы получают входы в порядке завершения (уже завершённые к старту — в
порядке входа); отмена ждущего запроса отменяет незавершённые входы, ждёт их
очистки и проваливает все запросы этой отменой с вторичными отказами.
Проба: порядок 1, 10, −20, 30 совпадает со sparrow-next; origin здесь
недетерминирован (порядок меняется между прогонами). Не перенесены (3c):
intrinsics `okkama.test.*` и `okkama.fake.storage.*`.

### Этап 3. Async

- Кадры async-функций, `await`, немедленный `spawn`, повторный await,
  несколько ожидающих, отмена (доставка в кадр, cleanup до завершения),
  группы, collect/race, каналы, события, блокировки, семафоры, таймеры,
  стримы — поверх Tokio-хоста и `native_io`.
- Ожидание внешнего I/O, диагностика простоя.

Готово, когда: async-тесты и выбранные L08-кейсы зелёные под клеткой;
`asyncs` и DB-бенчмарк не медленнее прототипа на порядок.

### Этап 4. Natives, std и CLI

- Перенос провайдеров (механически), SQLite, JSON, regex, сеть, файлы;
  `--test`, `--stats`, `--native-capabilities`.
- Conformance: SQLite-кейсы, L01–L13 по наборам (без workers).
- `sparrow-next` переключается на `sparrow-core`.

Готово, когда: все перенесённые тесты и conformance-наборы, проходившие
на `sparrow-engine`, проходят на новом ядре.

**3c и 4 выполнены 2026-11-06, кроме workers.** Провайдеры `sparrow-engine`
перенесены фасадом `host/` почти без изменений. Провайдер видит `Heap` с
прежними методами и `Slot`. Слот — типизированный вид слова core, а не копия:
строки, массивы и словари лежат в куче core, целые в пределах i64 передаются
без упаковки, дескриптор — id в арене хоста. На границе слова превращаются в
слоты по ABI-сигнатуре натива, результат — обратно. Дескриптор доходит до
программы маленьким объектом кучи core; куча наблюдает его, и со смертью
объекта состояние дескриптора освобождается. JSON-узлы размечаются от живых
дескрипторов после сборки. `NativeFailure` — объект встроенного типа и новый
вид отказа: ловится объектом NativeFailure и ролью Error, в отчёте —
«NativeFailure: сообщение».

Async-нативы (SQLite, сеть, процессы) — кадры-драйверы. Драйвер запускает
Rust-Future провайдера (`native_io`) и опрашивает её с waker'ом, который
называет кадр; waker срабатывает с любого потока (ответы SQLite-воркеров).
Когда очередь готовых пуста, планировщик блокируется в current-thread Tokio
до waker'а или ближайшего таймера (`io.rs`). Отмена вызывает cleanup-хук
провайдера и ждёт его.

`--test`: intrinsics `okkama.test.*` (ok/is/isnt/fail, показ значения по
статическому типу) и раннер; каждый тест — на свежем runtime. Бинарник
`sparrow-next` теперь собирается из `sparrow-core`; старый движок до этапа 6
остаётся бинарником `sparrow-engine` для сверок. Не перенесены: process
workers (`--worker`, `worker.spawn`/`worker.bind`; проверка возможна только
в Docker/VM), `--stats`, intrinsics `okkama.fake.storage.*`.

`core-compare.py` теперь запускает и кейсы с `--test`, аргументами, stdin,
переменными окружения, файлами и SQLite (каждому движку — своя копия папки
кейса). Полный прогон L00–L13 под клеткой: 421 совпадение, 0 расхождений; 11
unsupported — нативы, которых нет и в `sparrow-engine` (pcg, uuid, toml,
url_text, statistics, math_aggregate, secure_random, html,
unicode_normalization, debug). Пропущены parse/check-кейсы и кейсы с
сетью, workers и порождением процессов.

### Этап 5. Производительность и std/db

- Встраивание мелких функций, nursery (если R1 пересмотрен), профили.
- std/db: строки батчем (ответ fetch — Rust-данные, `Row` = батч + номер),
  колонка по номеру, лёгкий горячий путь `SqliteRows.row()`.
- Цель roadmap: SQL/DB не хуже 1.5× Python.

### Этап 6. Удаление старого ядра

- `sparrow-engine` удаляется, `sparrow-proto` — тоже; документация и
  roadmap обновляются.

## Риски

- **Объём переноса natives** — механический, но большой; API `Heap` держит его
  в рамках.
- **Семантика порядка в async** (немедленный старт, порядок пробуждений,
  отмена) — проверяется существующими async-тестами и L08.
- **Платформы:** frame records на aarch64 (x29) и x86_64 (rbp); Linux и macOS.
- **Отладка JIT** без интерпретатора: дамп CLIF по функции, `--stats`,
  дифференциальные прогоны против origin.
