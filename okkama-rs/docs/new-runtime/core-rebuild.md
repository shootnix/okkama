# Перестройка ядра Sparrow

Статус: план, согласован пользователем 2026-11-06. Основание —
[разведка ядра](core-spike.md): прототип `crates/sparrow-proto` под клеткой
быстрее текущего `sparrow-engine` в 23–40 раз и sparrow-origin в 9–15 раз,
на массовых спаунах — на порядки.

## Целевая модель

1. **Синхронные функции** компилируются целиком (Cranelift) и вызывают друг
   друга прямыми машинными вызовами на нативном стеке. Роли — таблица
   `[роль, слот][дескриптор]` и косвенный вызов; замыкания — косвенный вызов.
2. **Async-функции** — возобновляемые машины состояний. Кадр — объект кучи и
   одновременно Future. `await` готового — результат; холодного — запуск тела
   тут же; иначе — сохранить регистры, записаться ожидающим, уступить.
   `spawn` стартует немедленно. Планировщик и всё внешнее ожидание — на Tokio.
3. **Значения без тегов там, где тип статический.** Тег остаётся у `int`
   (малое / BigInt), `any`, `rat` и незаполненных полей.
4. **Объекты — указатели на `[заголовок, поля…]`**, поле читается по смещению
   в машинном коде, аллокация — инлайн.
5. **Точный GC.** Корни: stack maps Cranelift (проход по frame records), кадры
   async в куче, корни Rust-стороны через посетителей. GC запускается только
   в точках безопасности машинного кода и диспетчера, никогда внутри native.
6. **Вытеснения внутри синхронного кода нет** (уступка — только на `await`).
   На обратных переходах циклов — проверка флага прерывания: отмена задачи,
   таймаут теста и завершение процесса останавливают зависший цикл
   типизированной ошибкой, а не вытеснением.

## Что сохраняется

- Загрузчик, верификатор SPB, построение плана (`Op`), анализ живых значений,
  проверка ролей и сигнатур — вход нового JIT.
- Natives (~17 тыс. строк, включая SQLite) — через сохранённый API `Heap`
  (`text`, `elements`, `allocate_*`, `object_get`, handles). Меняется реализация
  API, не провайдеры.
- Async-хост на Tokio, `native_io` Request, семантика отмены, cleanup,
  `destroy`, ошибок и трасс.
- Тесты: все семантические проверки (программа → результат, вывод, ошибка).

## Что переписывается

- `execution.rs` (плоский диспетчер, continuations, saved), `jit.rs`
  (регионы, heap calls), `value.rs`/`arena.rs` (handles с поколениями, `Box`
  на объект), синтезированные cold-планы intrinsic (становятся обычными
  функциями ядра или прямыми вызовами Rust).
- Тесты внутренних свойств плоской модели (14 наборов используют
  `resume(1)`, `continuation_depth`, `saved_value_count`): переписать на свойства
  новой модели или удалить, если свойство исчезло.

## Решения (подтверждены пользователем 2026-11-06)

- **R1. GC без перемещения на первом этапе.** Mark-sweep с классами размеров,
  аллокация инлайн из свободных блоков. Natives держат значения в локальных
  переменных Rust между аллокациями, runtime-объекты (Atomic, Event, Lock,
  Channel…) сейчас ищутся в картах по адресу объекта — перемещение сломало бы
  и то и другое. Перемещающий nursery — отдельная оптимизация позже, когда
  идентичность вынесена в заголовок, а natives переведены на корни-области.
- **R2. Глубокая рекурсия — большой стек потока VM** (резерв 1 ГБ виртуальной
  памяти, физическая — по мере роста) вместо отката в интерпретатор. Исчерпание —
  типизированная ошибка переполнения стека, как сейчас ограничение памяти.
- **R3. Без cold-интерпретатора.** Один режим исполнения; функции
  компилируются лениво при первом вызове (заглушка вызова). `Mode::Cold`
  в тестах исчезает; дифференциальная проверка — против sparrow-origin
  и IR-интерпретатора на conformance.
- **R4. Новый crate `sparrow-core`**, а не правка `sparrow-engine` на месте:
  текущий движок работает до паритета, natives и тесты переносятся в новый
  crate по этапам, после паритета `sparrow-engine` удаляется. CLI `sparrow-next`
  переключается на новое ядро в конце этапа 4.

### Этап 3. Async — проект (2026-11-06)

Семантика переносится из `sparrow-engine` (`future.rs`, `execution.rs`
`await_future`/`unwind`/`take_cancellation`, `async_host.rs`
`drive_task`/`shutdown_tasks`); все прогоны — под `caged.py`.

**Кадр async-функции = её Future** (объект кучи `FRAME`), слова:
`[header, state, result, failure, waiter, awaiting, resume, flags, registers…]`.
state: COLD / RUNNING / DONE / FAILED (позже — внешние: timer, I/O, event…).
`failure` — ссылка (отдельно от `result`, чей вид задан типом результата).
`waiter` — 0, кадр или payload-список ожидающих (повторный await из разных
задач). `awaiting` — Future, которого ждёт этот кадр (цепочка до самого
внутреннего ожидающего кадра задачи — для доставки отмены). flags: spawned,
observed, cancel_requested, cancel_delivered.

**3a. Ядро:**
- тело async-функции компилируется как `(ctx, frame) -> 0 | 1` (готово /
  pending); вход по `resume`: 0 — старт с параметрами из кадра, `pc + 1` —
  повторный вход в `await` после загрузки всех регистров из кадра;
- вызов async-функции выделяет холодный кадр (`rt_future_new`);
- `await` → `rt_await(ctx, self, future)`: DONE — значение; FAILED — поднять
  отказ (observed); COLD — запустить тело тут же (Rust вызывает машинный код);
  иначе — записаться ожидающим, сохранить регистры, вернуть pending;
- неперехваченный отказ тела: вызывающий тело (await/планировщик) видит
  `status = FAILED` после возврата, переводит Future в FAILED, сбрасывает
  статус и будит ожидающих;
- `fut.spawn` — немедленный старт: тело работает до завершения или первой
  приостановки; отказ ребёнка остаётся в его Future, родитель продолжает;
- `fut` done/cancelled/cancel; отмена COLD — FAILED(Cancelled); RUNNING —
  флаг; доставка: самый внутренний ожидающий кадр задачи возобновляется,
  его `await` поднимает Cancelled, раскрутка выполняет обработчики и cleanup;
- `FailureKind::Cancelled` (catch: встроенный объект `Cancelled`, роль Error;
  текст «Cancelled: Operation was cancelled»);
- планировщик: очередь готовых; async `main`; по завершении корня — отмена
  ещё работающих порождённых задач, ожидание их завершения, затем отказ
  неотслеженной порождённой задачи становится итоговым (как в старом движке).

**3a выполнен 2026-11-06** (`tasks.rs`, JIT: вход async-тела по `resume`,
`await` с сохранением регистров, `rt_future_new`/`rt_await`/`rt_complete`/
`rt_spawn`/`rt_fut`; async-реализации ролей, `call.cap` и замыканий дают
холодный Future). Проверки под клеткой: прототип `asyncs` (131 тыс. спаунов,
100 тыс. await) — результат верен, ~0.33 с против ~10.5 с у origin; 10-app —
вывод совпадает, ~0.50 с против ~0.93 с; L08 — 12 кейсов совпадают, 0
расхождений, 14 ждут intrinsics. Ошибка по пути: заголовок кадра хранил
`objects.len() + функция`, а GC брал раскладку по индексу функции — сборка
читала чужую раскладку (segfault после первой сборки); исправлено.

**3b.** Таймеры (`sleep`) через Tokio; intrinsics Atomic, Event, Lock,

**3b выполнен 2026-11-06.** Модель: async-intrinsic и async-native — тоже
кадр-Future (холодный при вызове, как любая async-функция), но его «тело» —
Rust-драйвер (`drivers.rs`), а не машинный код; у кадра драйвера после
регистров одно трассируемое слово состояния (payload для групп, коллекций,
таймаутов). Ждущий драйвер помечается PARKED: на ресурсе (событие,
блокировка, барьер, канал, таймер) или на нескольких Future сразу
(`listen`); пробуждение — только через `wake`, повторно в очередь кадр не
попадает. Отмена, дошедшая до припаркованного драйвера, будит его с
DELIVER_NOW, и драйвер сам снимает заявку (из очереди блокировки, канала,
барьера, таймеров); у драйвера, чья заявка уже исполнена (выдана
блокировка, передано значение), отмена остаётся запрошенной до следующего
`await`. Очереди ресурсов пропускают кадры, которые уже не PARKED.
Состояние примитивов (`primitives.rs`) — в таблице по адресу владеющего
объекта; объект наблюдается кучей, состояние уходит вместе с ним; ждущие
кадры и хранимые значения — корни. Порядок завершения Future — в старших
битах flags (для Raced/FirstSuccessful/Before/Within). Синхронные
intrinsics разрешаются по имени один раз при загрузке; для вызова
native/intrinsic через таблицу кода (роль, замыкание) компилируется
трамплин. Таймеры пока ждёт сам планировщик (`thread::sleep` до ближайшего
срока, когда очередь пуста); Tokio придёт с I/O-natives (этап 4).

Проверки (все прогоны — под `caged.py`): L08 — 25 совпадают, 0 расхождений,
1 ждёт natives (`db.query-lifetime`); L01–L07 — 293 / 0 (было 287: прошли
кейсы с intrinsics через роль); L09/L12 — 22 / 0, остальные 31 ждут
natives. Пробы против origin, вывод совпадает: 300 задач на одной Lock со
сном внутри (счётчик 300), канал на 100 тыс. сообщений при ёмкости 0/1/16
(origin 0.84 с, core 0.34 с), отмена спящей 30 с задачи и выход с ещё
спящей задачей (мгновенно), Semaphore(4) на 100 задач (пик 4), Raced и
AllFutures на таймерах.

`FutureCompletions` (тоже 3b): прямой вызов `completion()` читает origins
сразу, как старый движок (JIT вызывает для него intrinsic, а не создаёт
холодный кадр); через роль или замыкание — при первом запуске драйвера.
Запросы получают входы в порядке завершения (уже завершённые к старту — в
порядке входа); отмена ждущего запроса отменяет незавершённые входы, ждёт их
очистки и проваливает все запросы этой отменой с вторичными отказами.
Проба: порядок 1, 10, −20, 30 совпадает со sparrow-next; origin здесь
недетерминирован (порядок меняется между прогонами). Не перенесены (3c):
intrinsics `okkama.test.*` и `okkama.fake.storage.*`.

### Этап 4. Natives, std и CLI

- Перенос провайдеров (механически), SQLite, JSON, regex, сеть, файлы;
  `--test`, `--stats`, `--native-capabilities`.
- Conformance: SQLite-кейсы, L01–L13 по наборам (без workers).
- `sparrow-next` переключается на `sparrow-core`.

Готово, когда: все перенесённые тесты и conformance-наборы, проходившие
на `sparrow-engine`, проходят на новом ядре.

**3c и 4 выполнены 2026-11-06, кроме workers.** Провайдеры `sparrow-engine`
перенесены фасадом `host/` почти без изменений. Провайдер видит `Heap` с
прежними методами и `Slot`. Слот — типизированный вид слова core, а не копия:
строки, массивы и словари лежат в куче core, целые в пределах i64 передаются
без упаковки, дескриптор — id в арене хоста. На границе слова превращаются в
слоты по ABI-сигнатуре натива, результат — обратно. Дескриптор доходит до
программы маленьким объектом кучи core; куча наблюдает его, и со смертью
объекта состояние дескриптора освобождается. JSON-узлы размечаются от живых
дескрипторов после сборки. `NativeFailure` — объект встроенного типа и новый
вид отказа: ловится объектом NativeFailure и ролью Error, в отчёте —
«NativeFailure: сообщение».

Async-нативы (SQLite, сеть, процессы) — кадры-драйверы. Драйвер запускает
Rust-Future провайдера (`native_io`) и опрашивает её с waker'ом, который
называет кадр; waker срабатывает с любого потока (ответы SQLite-воркеров).
Когда очередь готовых пуста, планировщик блокируется в current-thread Tokio
до waker'а или ближайшего таймера (`io.rs`). Отмена вызывает cleanup-хук
провайдера и ждёт его.

`--test`: intrinsics `okkama.test.*` (ok/is/isnt/fail, показ значения по
статическому типу) и раннер; каждый тест — на свежем runtime. Бинарник
`sparrow-next` теперь собирается из `sparrow-core`; старый движок до этапа 6
остаётся бинарником `sparrow-engine` для сверок. Не перенесены: process
workers (`--worker`, `worker.spawn`/`worker.bind`; проверка возможна только
в Docker/VM), `--stats`, intrinsics `okkama.fake.storage.*`.

`core-compare.py` теперь запускает и кейсы с `--test`, аргументами, stdin,
переменными окружения, файлами и SQLite (каждому движку — своя копия папки
кейса). Полный прогон L00–L13 под клеткой: 421 совпадение, 0 расхождений; 11

сетью, workers и порождением процессов.

### Этап 5. Производительность и std/db

**5a (2026-11-06): граница natives и строки БД.** Профиль `projection_only`
показал: дороже всего не SQLite, а вызовы natives (~12 на строку) — поиск
натива по строке символа на каждом вызове, перебор провайдеров, SipHash в
таблицах дескрипторов и ресурсов, временные `Vec`, вход в Tokio для
синхронных нативов. Теперь натив разрешается один раз на функцию, провайдер —
по таблице, хеш-таблицы на адресах — мультипликативный хеш, Tokio — только для
сетевых и процессных провайдеров; `rt_failure_op` больше не клонирует
инструкцию. Граница натива ~40 нс (микротест `bigint_valid`: остальные
~170 нс — разбор BigInt самим провайдером).

Строки SQLite больше не идут ячейка-за-нативом: пакет строк приходит
страницей простых значений (виды, целые/порядковые номера, вещественные,

`int`/`text`/`maybe` читают массивы без вызовов. Ручные строки и другие
драйверы сохраняют native-ячейки. DB-бенчмарк (под клеткой, мс, два прогона;
origin — со старым std, core — с новым `std/db`; контрольные суммы

**5b (2026-11-06): низкоуровневая работа с байтами и текстом.** Профиль
разбора ответа в стиле memcached (курсор в `Atomic`, поиск CRLF циклом,
`slice`, `Utf8Decoded`, `split`, `ParsedInt` — так написан и Postgres-клиент
std) показал: core был в 7 раз медленнее origin — `arr.slice` копировал весь
массив. Сделано в ядре (без изменений языка и std):

- `@byte` упакован (байт на элемент, флаг PACKED в заголовке массива; тип
  `Kind::Byte`); все места создания массивов с элементом byte упаковывают —
  по статическому типу регистра назначения; JIT читает `u8`; `heap.elements()`
  разворачивает упакованный массив для непереведённых путей;
- `Atomic` — ячейка кучи `[header, value, closed]` с раскладкой для GC;
  `value`/`replace`/`closed`/`close` компилируются инлайном;
- инлайн-пути JIT: `&`, `|`, `^`, `~`, унарный минус, сдвиги (с проверкой
  переполнения), `byte.from` из малого целого, `==`/`!=` строк по указателю
  и длине;
- строки с флагом ASCII: `length`/`slice` за O(1); `split` и `slice` без
  промежуточных копий; UTF-8 encode/decode одной копией; десятичные целые
  до 18 цифр без BigInt;
- регионы очистки: пустой регион закрывается без обхода, обход графа
  ресурсов отмечает объекты битом заголовка вместо хеш-множества.

Сверки с origin: 684 строки побитовых операций (граничные значения, большие
целые, сдвиги 0..63), 265 строк строковых операций (многобайтовые срезы,
split, UTF-8, разбор целых) — совпадают; conformance L00–L13 — 421 / 0.

**5c (2026-11-06): путь запроса.** Профиль VM-потока на точечных запросах:
SQLite-воркер занят ~6% времени, VM-поток — 80% (работа std/db и ядра) и 20%
ожидания. Сделано:

- ядро: регион — ячейка из одного слова (RegionValue создаётся при первом
  ресурсе), вход в регион — встроенная аллокация JIT, выход из пустого
  региона — одна проверка, регистрация — прямой helper с быстрым отказом
  для значений, не достигающих свободных ресурсов; `Event` — ячейка
  `[initial, set, waiters]`, `ready()` инлайном; `enum.case`/`enum.cmp`
  инлайном (были общим медленным путём — 41 вызов на одну вставку);
  дескрипторы natives — ячейки `[header, id]` без Rust-аллокации;
- ожидание воркера: планировщик и поток SQLite перед засыпанием крутятся до
  50 мкс (воркер отвечает быстрее, чем стоит пробуждение потока);
- `std/db` (поведение не меняется): `reply()` без FutureGroup/Event/объекта
  очистки — прямой `await` и тот же барьер `sqlite_settled` при отмене или
  отказе; форма результата (столбцы и схема строки) кэшируется в сессии;
- предвыборка первой страницы (`PREFETCH_FIRST_PAGE`) реализована, но
  выключена: она меняет момент первого шага SQLite (первое чтение курсора
  перестаёт быть точкой отмены, побочные эффекты `RETURNING` — раньше);
  решение — за пользователем;
- счётчики событий ядра: `SPARROW_CORE_STATS=1` печатает их при выходе.

DB-бенчмарк против Python 3.9 `sqlite3` (чередованием, медианы 5 прогонов,
мс): projection_only 3.5 / 5.2, scan_raw 7.7 / 16.0, scan_stream 10.1 / 25.9,

**5d (2026-11-06): регионы и привязка параметров.** Почему компилятор
выпускает регионы даже в однострочных методах: метод объекта с `destroy`
начинает с `region.adopt` своего `self` — временный ресурс, на котором вызвали
метод, уничтожается на выходе. Это модель владения, а не лишний код;
статически элидировать нельзя. Поэтому удешевлён рантайм: регион — массив
`[overflow, 4 слота]`, записи без Rust-аллокации и хеш-множества (линейный
поиск), переполнение — в `RegionValue`; пустой регион — проверка одного слова.

Протокол захвата значения (`DbValueCapture`: ровно одно событие объявленного
вида, затем значение, затем печать запечатана) перенесён из нативного
состояния в Okkama — флаги в одном `Atomic<int>`, та же семантика и тексты
ошибок; нативным осталось только создание ячейки. Сверка с origin на
некорректных принтерах (два события, чужой вид, нет события, запись после
запечатывания) — совпадает. Вставка: 19.2 → 8.4 мс (Python 0.7).

Проверка `std/db`: std репозитория сейчас не собирается целиком (идёт
миграция ошибок на error enum), поэтому изменённые файлы `std/db` и
`std/runtime/database.ok` проверяются в копии старого std
(`core-compare.py --core-stdlib`): L08/L09/L11/L13 — 77 совпадений,
0 расхождений. Осталось: `lookup_prepared` и `insert_transaction` (путь
запроса: параметры, пул, транзакция), `db_position` (натив на каждое чтение
поля), 04-bigint.

- Встраивание мелких функций, nursery (если R1 пересмотрен), профили.
- std/db: строки батчем (ответ fetch — Rust-данные, `Row` = батч + номер),

- Цель roadmap: SQL/DB не хуже 1.5× Python.

  аллокаций, длиннее — BigInt.
- std: `std/runtime/bytes.ok`, `std/encoding/bytes.ok` (`ByteSearch`,
  `ByteRange`, `InvalidByteDecimal`), 5 тестов — проходят на ядре.
- memcached-разбор (2000 записей): срезы + Atomic на ядре 3.2 мс/раунд →
  `encoding/bytes` 0.94 мс; Python (`bytes.find`/срезы/`int`) 4.5 мс.
  На запись — 9 вызовов нативов; дальше упирается в саму границу native
  (~50 нс с окружающим кодом), следующий шаг при нужде — интринсики JIT.

**5g (2026-11-06): `io/input`, ошибки интринсиков как error enum.**

- `ByteInput` (`std/io/input.ok`): буфер `Atomic<@byte>` + позиция; дочитка —
  `runtime/bytes` `bytes_join` (ABI 613: несъеденный хвост + новый кусок, одна
  копия), строки — `ByteSearch` с повтором только хвоста длиной терминатора.
  3 async-теста на поддельном читателе (`ChunkReading`) — проходят на ядре.
- `AsyncReading`/`AsyncWriting` перенесены в `io/stream` (решение пользователя):
  иначе `io/input` тянул бы немигрированную цепочку `net/stream` (16 модулей).
  Импорт поправлен в 35 потребителях; реэкспорта в языке нет.
- Ошибки, которые бросают интринсики, могут быть error enum: в таблице
  `related` компилятора — `"AtomicClosed.closed"`, case обязан быть первым
  (рантайм создаёт объект варианта с `$tag = 0`). Формат SPB/OIR не менялся:
  `thrown` в ядре, sparrow-vm (origin), IR-интерпретаторе
  (`ObjectHeap::raised_fields`) и план `AtomicClosed` в sparrow-engine
  собирают `[$tag, payload первого case в массивах из одного элемента, пустые]`.
  `async/atomic` мигрирован (`enum AtomicClosed is Error = (closed);`), вывод
  четырёх движков на закрытом `Atomic` совпадает.
- memcached-разбор потоком (куски по 4 КиБ, `line` + `ensure`/`skip`):
  3.2 мс/раунд на ядре против 10.7 мс у Python `asyncio.StreamReader`
  (`readuntil`/`readexactly`). Прямой разбор массива — 0.94 мс: разница —
  future на каждый `line`/`ensure`, копия заголовка и `Atomic` разбора.
- Сверки (репозиторный компилятор и std): conformance 343/343 совпадают,
  3 unsupported (нативы, которых нет в ядре), 334 кейса не собираются —
  немигрированные модули std. std-тесты затронутых префиксов: расхождений 0.

**5h (2026-11-06): process workers, память машинного кода.**

- `worker.rs`: OKW1 (формат `sparrow-engine`), но типизированный — слова
  ядра без тегов, значения кодируются и проверяются по типам параметров и
  результата функции-входа; обход — рабочими стеками. `worker.spawn` и
  `worker.bind` — общий путь `rt_exec` (spawn запускает драйвер сразу);
  Future воркера — кадр синтетической async-функции-интринсика
  `sparrow.worker.process` (по одной на тип результата, добавляет
  `Loaded::new`), драйвер опрашивает `worker_process::Request` (перенесён из
  sparrow-engine как есть) с waker кадра и держит кадр в `io.requests`.
  Привязка `worker.bind` — `State::WorkerBinding` на копии замыкания.
  Ребёнок: `sparrow-next --worker FILE.spb`, запрос из stdin,
  `Runtime::run_function_with`; `SPARROW_INTERNAL_WORKER` без `--worker` —
  отказ.
- Проверка в Docker (`rust:latest`, arm64, сеть выключена, лимиты CPU/памяти/
  процессов): `L08.spawn.worker-process` и свои сценарии (все переносимые
  типы, вложенные контейнеры, BigInt, вывод ребёнка, ошибка ребёнка,
  привязанное действие, брошенный воркер) — stdout, коды и тексты ошибок
  совпадают с `sparrow-engine`; после выхода процессов не остаётся.
  `L08.spawn.worker-rejects-objects` компилятор отвергает статически.
  Тесты `worker_process` (13/13 тестов крейта) — в контейнере.
- Найдено попутно: на AArch64 Linux cranelift-jit после каждого
  `finalize_definitions` делает `membarrier(PRIVATE_EXPEDITED_SYNC_CORE)`
  (IPI всем ядрам; первый вызов ещё и регистрирует процесс — ~4 мс) и
  отдельный mmap на каждую функцию. `code_memory.rs`: свой
  `JITMemoryProvider` — одна резервация на вид памяти, выделение подряд,
  при финализации `clear_cache` диапазона и `mprotect`, без барьера (код
  исполняет только поток VM). Старт в Docker: 7.9 → 1.4 мс (engine 1.0);
  программа с двумя воркерами: 21 → 6 мс (engine 9.8).

**5i (2026-11-07): Postgres-клиент страницами, точные флаги ресурсов.**

- Клиент читает DataRow как SQLite: `PgInput.data_rows()` отдаёт подряд
  идущие сырые сообщения одним куском, `PgOutcome` копит куски, нативный
  `runtime/postgres.pg_page(raw, width, oids)` разбирает порцию в `DbPage`
  (те же плоские колонки, коды ячеек 1 и 4 добавлены в `DbPage.cell`);
  `PgRows.row()` — `Row(DbRowData(schema, page, index))`. Объектов на
  колонку больше нет; `PgCell` и `PgDescription.row` удалены.
- `scan_all` (`Query.all`) остался квадратичным: 5000 строк ≈ 5 с, 20000 —
  OOM. Счётчики обхода графа ресурсов: track и kept-обход на каждую строку
  проходили ~2.5·n узлов, корень — `LinkedListCursor<Row>` из
  `QueryRowsCollected.values()`. Компилятор ставит `region.track` на
  `Cursor<Row>`, потому что plain-ность экземпляра роли он проверяет и по
  объявлению (`decl_plain_roles`): в программе с Postgres есть не-plain
  реализация `Cursor`, и все `Cursor<T>` становятся не-plain (в программе
  с SQLite такой нет — поэтому там не видно). Рантайм был ещё грубее: любая
  роль и любой `handle` в `descriptor_flags` считались ведущими к
  `destroy`, так что каждый узел списка и каждая строка получали
  идентичность, и обход шёл по всему хвосту списка.
- Исправлено в рантайме: роль (кроме встроенной `Error`) ведёт к тому же,
  к чему ведут объекты, которые её делают; `handle` — лист (обход в него и
  так не заходит). `scan_all`: 5000 строк — 12 мс, 20000 — 46 мс.
  Компилятор не менялся (нужно разрешение); общая цена трекинга —
  https://github.com/shootnix/okkama/issues/9.
- Проверка: конформанс 420 + 13 только-ядро DB-кейсов (по спецификации),
  тесты std 238 (190 как engine, 48 только на ядре; не проходят ICU и сеть
  в клетке). Бенч против `psycopg2` (Docker, 2 CPU, 5000 строк, медианы 5
  прогонов): projection 2.7/1.6 мс, scan_raw 8.3/4.0, scan_stream 11.1/6.0,
  scan_all 8.7/6.0, lookup_prepared 137/34 (500 запросов), lookup_statement
  130/35, insert_transaction 65/29.
- Точечный запрос: сэмплы gdb — ~70% времени VM в `wait_external`. Tokio
  однопоточный и крутится только в `block_on`, а ожидание сначала 50 мкс
  крутилось на флаге, который для сокетов никто не выставит (крутилка — для
  воркеров SQLite): 4 ожидания на запрос ≈ 200 мкс. Теперь каждые 64 оборота
  `block_on(yield_now())` — опрос реактора без блокировки. Медианы 9
  прогонов против `psycopg2`: projection 2.7/1.6, scan_raw 7.2/4.1,
  scan_stream 9.9/6.0, scan_all 7.6/6.0, lookup_prepared 46.9/34.4,
  lookup_statement 55.5/35.0, insert_transaction 23.9/29.1. SQLite без
  изменений. Остаётся второй круг на запрос (Sync после конца портала):
  отложенный Sync теряет ошибку коммита в autocommit, Execute(0)+Sync
  дорого закрывает большие выборки раньше времени — пока не трогаем.

### Этап 6. Удаление старого ядра

Условие: нативы. Ядро взяло набор провайдеров `sparrow-engine`, а тот
переносил нативы из origin (`okkama-runtime-core`/`sparrow-runtime`) не
до конца: из 613 символов ABI в ядре нет 199 — ini 17, application 16,
toml 16, html 12, tls_transport 12, x509 11, template 10, csv_state 8,
debug 8, pem 8, random_distribution 8, statistics 8, unicode_character 8,
uuid 8, random 7, time_zone 7, io_decorators 6, time_format 5 и мелочь
(account, layout, system, collections, crypto, collation, diff, format,
hpack, locale, math_aggregate, unicode_normalization, url_text). В
`sparrow-engine` нет тех же (и ещё 9). Пока их нет, 33 модуля std падают
на ядре (на IR-интерпретаторе их тесты проходят). Перенести из origin до
удаления старых движков и до переключения рантайма по умолчанию.

Сделано (2026-11-07): `host/native_origin.rs` — мост к реализациям origin
(`okkama_runtime_core::native::execute`): аргументы и результаты по типам
ABI, `any` — по типу программы (`host/native_debug.rs`), объекты provider —
`Handle::Origin`. Закрыто 182 натива и `runtime/debug` (`data_keys`/
`data_items` — в ядре, части остаются словами ядра). Не перенесены: TLS и
терминал (async, поверх сокетов ядра). Форматы (ini, toml, template, html,
csv, …) — кандидаты на переписывание на Okkama; криптография (tls, x509,
crypto, pem, хеши) остаётся нативной (решение пользователя).

Сделано (2026-11-07): TLS и терминал — ядро поддерживает все 621 натив ABI
(`sleep_nanoseconds` — драйвер). `host/native_tls.rs`: rustls поверх
`Transport` ядра (сокет забирает `Stream::take_for_tls`), без потоков и
мьютексов — шифротекст и открытый текст ложатся в буферы в том же опросе,
записи — в очередь в порядке провода, так что отмена не теряет байты;
наборы, лимиты, `authorize` через `x509.verify_chain` (мост origin) и тексты
отказов — как у origin. Терминал — мост origin и для async: обещание origin
(`resolved` или `offload`) оборачивается в future ядра; рабочие потоки origin
после доставки зовут хук `sched::set_wake`, future ядра делает
`sched::pump()`; отмена в ядре отменяет обещание. Проверено в Docker против
`sparrow`: TLS 1.3/1.2, ALPN, эхо 100 КБ, двусторонний shutdown, запись после
close, чужое имя и пустое доверие; pty — строка, raw, изменение размера.


- `sparrow-engine` удаляется, `sparrow-proto` — тоже; документация и
  roadmap обновляются.

## Риски

- **Объём переноса natives** — механический, но большой; API `Heap` держит его
  в рамках.
- **Семантика порядка в async** (немедленный старт, порядок пробуждений,
  отмена) — проверяется существующими async-тестами и L08.
- **Платформы:** frame records на aarch64 (x29) и x86_64 (rbp); Linux и macOS.
- **Отладка JIT** без интерпретатора: дамп CLIF по функции, `--stats`,
  дифференциальные прогоны против origin.
