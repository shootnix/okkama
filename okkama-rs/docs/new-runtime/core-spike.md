# Прототип ядра: прямые вызовы и объекты-указатели

Статус: разведка, 2026-11-06. Код — `crates/sparrow-proto`. Цель — проверить,
даёт ли другая модель исполнения кратный выигрыш, прежде чем перестраивать
ядро `sparrow-engine`.

## Почему

Профили `sparrow-next` (дорожка «Накладные расходы» в roadmap) показали, что
главная цена — модель исполнения, а не отдельные операции:

- плоский диспетчер: каждый вызов и возврат проходит через цикл в Rust
  (выход из JIT, сохранение регистров, вход), около 44% времени DB-пути;
- JIT регионами по 64 инструкции, всё нескалярное — через общий helper
  с `match` по `Op`, хотя типы регистров SPB статические;
- объект — handle (индекс + поколение) в арене и отдельный `Box` на объект.

Плоский диспетчер нужен, чтобы любой кадр можно было приостановить. Но
`await` разрешён только в async-функциях (компилятор и верификатор IR),
поэтому синхронному коду приостановка не нужна.

## Что делает прототип

Только синхронное подмножество (`const`, `int.add/sub/mul/mod/cmp`, `br`,
`jmp`, статический `call`, `ret`, `move`, `obj.new/get/next`, `trap`):

- функция компилируется целиком, все функции — в одном модуле Cranelift;
- вызов — прямой машинный `call`, аргументы и результат в регистрах ABI;
- регистры без тегов (типы статические); объектные регистры объявлены для
  stack maps Cranelift, поэтому вызовы уже платят spill, нужный точному GC;
- на входе функции — проверка запаса стека; отказ — статус в контексте,
  проверяемый после каждого вызова (так будут распространяться ошибки);
- объект — указатель на `[заголовок, поля…]`, bump-аллокация прямо в коде;
- переполнение `int` останавливает исполнение статусом (быстрый путь
  с проверкой переполнения такой же, как будет с переходом в BigInt).

Harness вызывает горячие функции напрямую: `Fib.fib(Fib(), 32)` для
02-calls и `World.simulate(world, id, 2500)` для `id` в `0..400` для
07-objects. Результаты совпадают с выводом sparrow-origin.

## Результаты (macOS arm64, release, повторяемо ±10%)

| Программа | Python 3 | sparrow-next | sparrow-origin | прототип |
|---|---:|---:|---:|---:|
| 02-calls: fib(32), 7 млн вызовов | 416 мс | 240 мс | 120 мс | ~20 мс |
| 07-objects: 1 млн неизменяемых шагов | — | 150 мс | 70 мс | ~7.7 мс |

Время origin и next — весь процесс; запуск, загрузка и компиляция std
у обоих < 10 мс. Компиляция прототипа — 1–2 мс.

## GC на stack maps (вторая итерация)

Копирующий сборщик Cheney на двух полупространствах — самый требовательный
вариант: объекты переезжают, все ссылки в машинных кадрах переписываются.

- Корни: проход по frame records (`preserve_frame_pointers`) от runtime-функции
  аллокации вверх; в каждом JIT-кадре — слоты из `user_stack_maps` по адресу
  возврата (SP вызывающего = FP вызываемого + 16 на aarch64); плюс корень harness.
- Какие поля — ссылки, известно из статических типов (объекты, successor, роли).
  Заголовок `descriptor << 1`, переадресация — `новый адрес | 1`.
- Если после сборки места нет, сборка повторяется в удвоенное пространство.
- Добавлены `role.wrap` (тождество: роль — тот же указатель) и `call.role`
  (дескриптор из заголовка → таблица `[роль, слот][дескриптор]` → косвенный вызов).

Проверка — отдельная программа `tree` (дерево через роль `Tree`: 20 раундов
по дереву глубины 16 и 12, рекурсивная сборка и обход): ссылки внутри объектов,
сотни тысяч живых объектов, глубокая рекурсия в корнях. Результат совпадает
с origin и next при любом стартовом размере пространства, от 1 КБ (23 сборки,
рост до 8 МБ) до 4 МБ; 07-objects при 4 КБ — 11 909 сборок, результат верен.
Прогоны под `tools/new-runtime/caged.py`.

| Программа | sparrow-next | sparrow-origin | прототип (в т.ч. GC) |
|---|---:|---:|---:|
| tree, без клетки | 635 мс | 335 мс | 26 мс (GC 3.5 мс, 19 сборок) |
| tree, под клеткой (E-ядра) | 1.87 с | 1.09 с | ~60 мс |
| 07-objects, без клетки | 150 мс | 70 мс | 7.7–11 мс |

Сборщик без поколений копирует всё живое дерево (~2 млн слов за прогон) —
около 14% времени tree; поколенческий nursery уменьшит это для долгоживущих
данных. Вывод: точный перемещающий GC на stack maps Cranelift работает и
дёшев; это снимает главный риск модели «нативный стек + прямые вызовы».

## Бесстековый async (третья итерация)

Все запуски — под `tools/new-runtime/caged.py` (E-ядра, без fork и сети,
лимит CPU-секунд, RSS-сторож).

- Async-функция компилируется в возобновляемую машину состояний. Её кадр —
  объект GC-кучи `[заголовок, состояние, результат, ожидающий, точка
  возобновления, регистры…]`; кадр вызова async-функции и есть её Future.
- Вызов async-функции выделяет холодный кадр прямо в машинном коде.
- `await` готового Future берёт результат; холодного — запускает тело тут же
  обычным машинным вызовом; иначе кадр сохраняет регистры, записывается
  ожидающим и возвращает pending. Повторный вход — в ту же инструкцию `await`
  после загрузки регистров из кадра.
- `spawn` — немедленный старт (как в языке): тело ребёнка работает на текущем
  стеке до завершения или первой приостановки.
- Завершение будит ожидающего через очередь готовых; планировщик в Rust
  возобновляет кадры. GC трассирует кадры по типам регистров, очередь — корни.

Программа `asyncs`: дерево спаунов глубины 16 (131 070 спаунов и await
порождённых задач) и 100 000 последовательных await холодных Future
(рекурсивная цепочка глубины 1000, 100 раундов). Результат совпадает с origin
и next; при пространстве 1 КБ — 2123 сборки с переносом кадров и очереди.

Первая версия ставила `spawn` в очередь (обход в ширину): все 2^17 кадров
жили одновременно, GC занимал 40–60 мс из ~60. Немедленный старт даёт обход
в глубину: GC 0.1–0.2 мс.

## Итог разведки (всё под клеткой, одинаковые условия)

Для origin и next — время процесса за вычетом запуска под клеткой
(~0.13–0.17 с, замер на 00-hello); для прототипа — время исполнения.

| Программа | sparrow-next | sparrow-origin | прототип | к next | к origin |
|---|---:|---:|---:|---:|---:|
| 02-calls (fib 32) | 0.77 с | 0.31 с | 34 мс | 23× | 9× |
| 07-objects | 0.48 с | 0.20 с | 13 мс | 37× | 15× |
| tree (граф, GC) | 1.74 с | 0.92 с | 60 мс | 29× | 15× |
| asyncs (спауны, await) | 0.44 с | 10.6 с | 11 мс | 40× | ~950× |

Стековые корутины origin на массовых спаунах проигрывают в разы даже
текущему next; бесстековые кадры дешевле обоих.

## Чего в прототипе нет (и что это стоит)

- **GC.** Без поколений, только aarch64 (frame records на x86_64 — rbp,
  та же схема), без финализации/destroy.
- **BigInt.** Только быстрый путь; медленный путь не влияет на горячий код.
- **Async-периферия.** Отмена, группы, каналы, таймеры, I/O через Tokio —
  не проверены; модель кадров для них та же (pending + пробуждение).
  Нет списка ожидающих (один ожидающий на Future).
- **Ошибки и обработчики**, natives, роли, строки, массивы, замыкания.
- **Вытеснение** внутри синхронного кода (fuel) — по решению пользователя
  не требуется: синхронный код уступает на `await`, как в JS/Tokio.

## Вывод

Все три риска модели «синхронный код — нативный стек и прямые вызовы, async —
бесстековые кадры в куче, точный перемещающий GC на stack maps Cranelift»
проверены и дают кратный выигрыш: 9–15× к origin и 23–40× к sparrow-next на
ядре, и на порядки на массовых спаунах. Потолок текущей архитектуры — в модели
исполнения и представлении объектов; локальными правками он не снимается.
Рекомендация — перестроить ядро `sparrow-engine` под эту модель, сохранив
загрузчик и верификатор SPB, natives (через API Heap), async-хост на Tokio,
семантику ошибок/cleanup/отмены и весь набор тестов.
