# Порядок работы над новым Sparrow

Согласовано с пользователем 2026-11-03. Основные требования:
[roadmap](../sparrow-new-runtime-roadmap.md).

## Цикл каждой итерации

1. Прочитать этот файл и текущий шаг, затем критерии соответствующей фазы roadmap.
2. Выбрать первый незавершённый доступный шаг по таблице ниже. Наличие кода или
   старого частичного отчёта не означает выполненного критерия.
3. До изменения определить конкретный пробел, минимальное исправление,
   ожидаемое поведение, риск и безопасную проверку. Сохранять архитектуру и API.
4. Выполнить небольшой связный объём работы и подходящую проверку.
5. Записать результат, артефакты, ограничения и невыполненные проверки в roadmap
   либо связанную матрицу доказательств. Обновить текущий шаг этого файла.
6. Снова прочитать этот файл, выбрать следующую задачу и продолжить без ожидания
   разрешения на каждую уже авторизованную правку. При новой инструкции пользователя
   скорректировать порядок. Не выдавать план или наличие теста за успешный прогон.

Если проверка заблокирована средой, оставить её открытой и записать причину.
Продолжать безопасные задачи того же этапа или подготовку ближайшей зависимости;
не считать этап закрытым и не уходить к произвольным поздним возможностям.
Async-корни учитываются в памяти, cleanup — в вызовах уже на ранних этапах.

## Ограничения запусков

- На компьютере пользователя не запускать реальные process workers, массовые
  probe/conformance suites, стресс или длительную рекурсию без строгой изоляции.
- Таймаут, `nice`, `--jobs 1`, sampled RSS/PID monitor и process groups сами по себе
  не обеспечивают жёсткую изоляцию. Нужны внешние лимиты всего дерева процессов
  и всей VM/контейнера, ограниченный вывод и гарантированное завершение среды.
- До запуска неизвестного теста прочитать его и вызываемый им launcher.
  Безопасные конечные проверки выполнять последовательно; сборка — один job.
- Не завершать посторонние процессы. Не запускать Docker/VM автоматически
  лишь для снятия отметки BLOCKED. Отсутствие среды не препятствует статическому аудиту.
- Async-, spawn- и стресс-пробы внутри одного процесса (без process workers) —
  только через [`tools/new-runtime/caged.py`](../../tools/new-runtime/caged.py):
  `taskpolicy -b` (энергоэффективные ядра, низкий приоритет), `sandbox-exec`
  без порождения процессов, сети и записи вне `--writable`, `ulimit -t`
  (жёсткий лимит CPU-секунд), RSS-сторож и таймаут `probe_process`. Проверено
  2026-11-06: fork запрещён, бесконечный цикл убит SIGXCPU, рост памяти остановлен.
  Это не VM: реальные process workers — только в Docker/VM с лимитами cgroup,
  daemon запускает пользователь. Время под клеткой медленнее (E-ядра): сравнивать
  движки только в одинаковых условиях.

## Текущий шаг

С 2026-11-06 главная работа — [перестройка ядра](core-rebuild.md). Решения R1–R4
подтверждены; этап 0 (контракты, разметка 286 тестов, каркас `sparrow-core`)
выполнен. Текущий — этап 1: куча и значения.

шаги 0–6 идут параллельно основной последовательности, без изменений компилятора
и IR-интерпретатора. Бенчмарки запускать только короткими одиночными прогонами.

Порядок сохранён; новая функциональность фазы 7 отложена.
Изоляция для опасных запусков пока не подтверждена, реальные workers не проверять.
Создана [матрица фаз 0–1](foundation-evidence.md). Исправлены placeholders
генератора inventory: неизвестная поддержка больше не объявляется отсутствующей.
Исторические снимки сохранены. Offline boundary guard прошёл для трёх пакетов.
Сопоставление выполнено: [foundation-audit.json](foundation-audit.json),
1922 совпадающих исходника, 1022 compile-записи с runtime NOT_RUN, 900 OCS-исходников
требуют отдельной сверки отчётов. У 436 контрактов нет явной case-связи.
Языковые контракты без связей разобраны: все три официально deferred;
генератор теперь сохраняет status/aspects/discrepancies. Аудит различает

и 64 deferred/informative. Четыре чистых unit-теста аудита прошли.
Сопоставлены исторические результаты: 835 OCS-кейсов совпадают по полному набору
хешей файлов кейса, 239 stdlib-модулей — по хешу исходника. Это historical_pass
эталона, не PASS нового runtime; зависимости stdlib и среда этим не доказываются.
Пять чистых тестов аудитора прошли. Инвентаризацию не расширять ради самой отчётности.
ABI-документ сверен с текущими статусами и ownership, устаревшие утверждения
исправлены. Три точечных теста bootstrap/JIT-регионов прошли; команды и ограничения
в foundation-evidence.md. Полные фазы 0–1 остаются открытыми.

нет fallback, GC освобождает мёртвые значения, новая сессия может повторить компиляцию.
Создана [матрица ABI → тесты](abi-evidence.md), platform/OS failures отмечены
отдельно. Точечные live-call, tail-arguments и suspension-spills проверки прошли.
Выбранные lifetime/exception циклы ограничены; CodeMemory ownership,
exceptional spills и parked roots проверены. Дополнительная серия: 13 PASS,
включая все восемь потребителей изменённого failure helper; детали в abi-evidence.md.
Проверены cleanup, closure и failure roots: ещё 7 PASS. Native failure тест
усилен сборкой через единственный cached Future root и проверкой освобождения.
Closure/resource циклы ограничены, все затронутые проверки прошли.
