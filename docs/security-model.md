# Модель доверия Okkama

Состояние на 0.3.3. Документ перечисляет, какой ввод Okkama обрабатывает
безопасно, где граница проходит сегодня и какие задачи
[дорожной карты «Укрепление»](roadmap/hardening.md) её сдвигают. При
закрытии каждой задачи P0/P1 этот документ обновляется в том же изменении.

«Безопасно» здесь значит: недоверенный ввод не приводит к повреждению памяти
и аварийному завершению процесса, а ошибка программы возвращается
структурированной ошибкой. Ограничение времени, памяти и прав доступа —
отдельный вопрос; он описан для каждой границы.

## Кратко: как запускать недоверенное

| Что | Сегодня |
|---|---|
| Исходник Okkama | можно разбирать и проверять (`okkama check`) в своём процессе; компиляцию больших исходников — с внешним ограничением времени и памяти |
| Байткод `.spb` | исполнять только в отдельном процессе и с `OKKAMA_JIT=off` |
| Программа Okkama | исполнять только в отдельном процессе с ограничениями ОС (время, память, файловая система, сеть) |
| Встраивание `sparrow-vm` / `okkama-runtime` | только для доверенных программ; одна VM на поток |

## 1. Исходник

**Гарантировано.**
- Лексер завершается на любом тексте и не паникует; каждый токен лежит на
  границе символов UTF-8 (тесты `lexer_terminates_on_arbitrary_bytes`).
- Парсер ограничивает глубину своей рекурсии (`max_nesting = 64`) и дерево
  после разбора: глубина не больше 128 уровней, не больше 2^20 узлов; файл с
  заведомо большим числом токенов отвергается до разбора (H-03, 0.3.3).
  Цепочка из миллиона операторов отвергается любой командой за доли секунды.
- Синтаксическое дерево освобождается без рекурсии (H-03).
- Тексты больше 4 ГиБ не принимаются (`SourceFile`).
- Кампания из 6 000 случайных и мутированных входов (2026-11-01) не нашла
  зависаний и аварийных завершений `okkama check`.

**Не гарантировано.**
- Время и память компиляции большого корректного исходника: квадратичные
  места найдены и исправлены не все (H-39, H-28), бюджета специализаций
  generic нет (H-15).
- Отсутствие паник во всех фазах доказано только для лексера; фаззинга с
  обратной связью по покрытию нет (H-17).

**Рекомендация.** Недоверенный исходник компилировать с внешним
ограничением времени и памяти (`ulimit -v`, `timeout`) или в отдельном
процессе.

## 2. Байткод `.spb`

**Гарантировано.**
- Декодер проверяет магию, версию, переполнение чисел LEB128 и то, что
  счётчики элементов не больше оставшихся байтов; файл больше 256 МиБ не
  читается.
- Каждый путь исполнения проходит верификатор
  ([okkama-sparrow/src/verify.rs](../okkama-rs/crates/okkama-sparrow/src/verify.rs)):
  границы регистров, переходов и таблиц, запись регистра до чтения на всех
  путях, обработчики.
- Ошибка типа операнда или арности, пропущенная верификатором, ловится при
  исполнении проверкой тега значения и даёт структурированную ошибку.
- JIT не компилирует функции больше 2^14 регистров и с машинным кадром
  больше 1 МиБ, а вызовы функций больше 512 регистров делает через помощник
  (H-02, 0.3.3): смещения регистров не переполняются, кадр вызываемой
  укладывается в проверяемый запас стека.

**Не гарантировано.**
- Верификатор не проверяет типы операндов и арность вызовов (H-05), а JIT
  доверяет объявленным типам регистров при освобождении значений.
- Прямые обращения JIT к полям `Value`, `Object`, `Array` опираются на
  раскладку, найденную пробой при старте, а не на зафиксированный ABI (H-07).
- Память, нужная декодированной программе, не ограничена бюджетом (H-11).

**Рекомендация.** Недоверенный `.spb` исполнять только в отдельном процессе
и с `OKKAMA_JIT=off`, пока не закрыты H-05, H-07 и H-11.

## 3. Natives

Программа Okkama через std имеет полный доступ к файловой системе, сети,
процессам, окружению, часам и случайным числам хост-процесса. Модели
разрешений нет (H-14).

**Рекомендация.** Ограничивать средствами ОС: отдельный пользователь,
песочница, контейнер, сетевые правила.

## 4. Исполнение и встраивание

**Гарантировано.**
- Ошибка программы — trap (деление на ноль, выход за массив), `panic`,
  неперехваченный `throw`, отказ native — возвращается как ошибка со стеком
  вызовов Okkama и не завершает процесс.
- Целые точные: переполнения нет, `int` переходит в BigInt.
- Рекурсия Okkama не растит стек процесса: интерпретаторы держат кадры в
  куче, JIT при малом запасе стека передаёт вызов интерпретатору.
- Паника внутри помощника JIT перехватывается внутри помощника и становится
  внутренней ошибкой исполнения.

**Не гарантировано.**
- Нет бюджета времени: бесконечный цикл не прерывается (H-04).
- Нет бюджета памяти: глубокая рекурсия и большие коллекции занимают память
  без предела; неудачное выделение памяти в Rust завершает процесс (H-04).
- Цикл интерпретатора не перехватывает панику из-за внутренней ошибки
  рантайма; после внутренней ошибки состояние VM не определено (H-14).
- Вложенные исполнения из рантайма (колбэки intrinsic, тела `destroy`)
  наращивают стек Rust без счётчика глубины (H-12).
- `Value` построен на `Rc` и не `Send`: один экземпляр VM — один поток.
- В режиме процесса-воркера (`spawn`) рантайм завершает процесс сам
  (`std::process::exit`); этот режим не предназначен для встраивания.

**Рекомендация.** Недоверенные программы — только отдельным процессом с
ограничениями ОС, как устроены `spawn`-воркеры. Встраивание в процесс —
для доверенного кода, пока не закрыты H-04, H-12 и H-14.
