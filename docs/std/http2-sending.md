# Internal HTTP2 DATA scheduling

`Http2DataScheduler(output,peer,maximum[,chunk])` manages sender connection/stream windows and bounded active stream slots. maximum is 1..256; chunk is 1..16384, default 16384. Actual frame size is also bounded by current peer SETTINGS, connection/stream available credit and output storage. `open(stream)` accepts strictly increasing odd uint31 IDs; `close(stream)` retires a slot, frees capacity and prevents reuse. Late WINDOW_UPDATE on closed/implied-closed older odd IDs is ignored; future/unsupported stream IDs are connection errors. Physical stream admission, peer concurrent-stream limits and message half-close remain the owning session's checks.

`data(stream,bytes,end_stream)` returns a lazy supervised Future for at most 1 MiB captured input. One producer can run per slot. It offers one DATA frame at a time and awaits its ticket before offering the next. Ready sibling streams queue FIFO behind already pending work; zero-credit streams suspend outside the wire writer. Payload/empty terminal DATA follow signed windows: negative SETTINGS windows block payload while zero-length END_STREAM costs no credit. This does not acquire/read an application BodyOpening or validate outbound Content-Length.

Reservations are separate from wire window values. `Http2OutputStarting.start()` commits both window debits immediately before physical writing. Cancelling an unstarted ticket releases its reservation; cancelling a started frame preserves its debit and lets the connection writer finish it. WINDOW_UPDATE overflow is checked against the real window, so an unsent reservation cannot hide it. SETTINGS changes preflight all adjusted windows, cancel unstarted grants and wake producers to retry with current parameters. Closing a stream wakes its waiter; connection owners must call `stop()` on failure/closing to wake credit waiters and stop admission.

Full output queues suspend DATA producers on a generation event; synchronous control admission remains bounded and fails instead of blocking the sole reader. The connection owner must dispose physical transport after writer failure and propagate stop to producers. The scheduler retains no closed stream objects or completed frame history. Stream/window updates are synchronous under one interpreter; no host-thread synchronization is promised.
