# Scoped Basic and Bearer HTTP authentication

`BasicCredentials(username is string,password is SecretBytes)` exposes username() only; password is private. The initial preemptive profile supports ASCII credentials: username at most 1024 characters, no controls/colon; password at most 4096 bytes, printable ASCII (including spaces/colon). BasicAuthorization is an explicit wire-serialization capability producing the standard Base64 user:password field. No challenge charset negotiation or implicit UTF-8/NFC profile is claimed. [RFC 7617](https://www.rfc-editor.org/rfc/rfc7617.html) defines the wire representation and control/colon constraints.

`BearerAuthorization(token is SecretBytes)` is an explicit wire capability; size 1..8192. Serialization accepts ASCII letters/digits and -._~+/, with optional trailing = padding, rejecting spaces/non-ASCII/misplaced padding with a fixed reason. Header framing limits still apply independently. [RFC 6750 section 2.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.1) defines this Authorization syntax. No query/body token fallback is used.

`BasicExchanging(Exchanging,scope is Url,BasicCredentials)` and `BearerExchanging(Exchanging,scope is Url,BearerAuthorization)` implement Exchanging. Configured scope must be HTTPS without userinfo/query/fragment and must have valid positive/default port and host coordinates. Match canonical scheme/host/effective port plus normalized path with a segment boundary. Traversal outside scope and encoded slash/backslash paths receive no configured credentials. Outside scope, delegate the caller's request unchanged without exporting the configured secret. Inside scope, any explicit Authorization conflicts before export/delegation (AuthenticationConflict).

These adapters require a conforming verified-HTTPS Exchanging consumer; HttpClient provides that transport. An arbitrary custom implementation must uphold its HTTPS contract. The scope matcher cannot prove TLS behavior of caller-supplied code from a URL alone. Actual local HTTPS fixtures verify DNS/IP identity and no HTTP bytes on certificate-name failure.

For redirect-aware preemptive scope, place Redirecting outside the auth adapter. Generated Authorization stays internal to its direct hop; ClientResponse reports the original caller Request. The next hop therefore re-evaluates path/origin scope rather than inheriting a generated credential. Redirecting additionally strips caller authorization on origin changes. Putting auth outside an internally redirecting origin cannot inspect hidden hops and is unsuitable for enforcing scope per hop.

InvalidAuthentication exposes fixed reasons, never token/password values. Credentials/secrets have no implicit text observation. Explicit wire serialization/ExportedSecret deliberately expose caller-authorized data; resulting Header values are ordinary HTTP wire values and should be handled as such. The adapter neither opens/measures bodies nor retries 401 or replays a body. Underlying response ownership/errors remain intact. No MD5, NTLM or platform credential negotiation is introduced.
