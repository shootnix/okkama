# Владение ресурсами и SQL scopes

Новый ресурс, записанный в поле строящегося объекта, принадлежит его построению.
Выход из внутреннего `try` или `if` не должен его закрывать. При успешном создании
ресурс следует за готовым владельцем; при ошибке создания освобождается при
раскрутке конструктора. Borrowed-ресурс внешнего scope сохраняет своего владельца.
Посторонний временный объект внутреннего блока заканчивает жизнь в этом блоке.
Тот же механизм удерживает поля незавершённого successor. Это правило времени
жизни, а не повторный запуск конструктора или изменение приватности полей.

Для переносимого SQL-соединения сохраняется явный порядок:

```okkama
let connection=await storage.connection();
defer await connection.settled();
defer connection.close();
let rows=await connection.rows(statement);
defer rows.close();
```

Отложенные операции выполняются в обратном порядке: сначала reader, затем close,
затем awaited settlement. Одна локальная `close()` не всегда означает, что удалённый
сервер уже освободил сессию. В текущем bridge-адаптере эту работу выполняет
`settled()`. Завершение body и ошибки cleanup сохраняются отдельно механизмом
`defer`; ручной `catch` с новым throwing cleanup требует особой осторожности.

Если соединение передаётся долгоживущему UOW, cleanup открытия должен выполняться
только до передачи. `CommandStore.opened` использует существующий `Event` как
явный флаг publication и conditional deferred expression. После успешного создания
`RecordedCommand` ответственность переходит его вызывающему коду. Если BEGIN
падает и settlement тоже падает, основная ошибка BEGIN остаётся основной,
а cleanup хранится как secondary diagnostic. Это проверенный узкий путь открытия,
не обещание о каждом произвольном пользовательском `catch`.

`DbPool` уже предоставляет lease close, отзыв readers, rollback активной
транзакции и ожидание reset через `settled()`. `DbAcquiring` отдельно передаёт
prepared capability; portable connection не раскрывает её через downcast.
`FutureScope` управляет дочерними Future, но не выбирает SQL commit за приложение.

COMMIT с потерянным ответом сохраняет `IndeterminateCommit`. Нельзя объявлять его
успехом, выполнять вводящий в заблуждение rollback после возможного commit или
создавать новый operation/provider key. Проверка durable record с прежним ключом
остаётся отдельным действием. Владение ресурсом и номер версии не устанавливают
финансовую атомарность либо unforgeable authority.

Текущий PostgreSQL bridge-адаптер закрывает физическую сессию в `settled()`, поэтому
возврат capacity в pool не обещает повторное использование этой физической сессии.
Для native SQLite штатные pool/prepared/transaction тесты проверяют собственные
контракты. Сбой целого процесса требует серверной политики cleanup: IMP-22
добавил ограниченный idle lease и проверил kill/cancel/COMMIT-loss отдельно.

В HTTP/1 асинхронная очистка старта обмена и чтения тела сначала отменяет
дочерние операции и дожидается их завершения, затем закрывает транспорт и
завершает его очистку. Это сохраняет `Cancelled` при отмене ожидания заголовков
или тела. Пример проверки с реальным локальным peer:
`improvements-roadmap/results/IMP-14/verify.py`; политика JsonHttp и лимит65536
байт сохраняются. Синхронные close/abort и отдельные протокольные пути имеют
свои контракты; проверка этих двух async-путей не заменяет их проверку.
