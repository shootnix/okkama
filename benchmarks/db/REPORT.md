# SQLite DB API: Okkama против Python

Дата: 2026-11-02. Базовый замер и последующие эксперименты текущей рабочей ветки. Последний результат — в разделе «Нативное ядро DB».

## Главный результат

На выбранных задачах in-memory SQLite новый DB API Okkama существенно медленнее
Python `sqlite3`. На Sparrow потоковое чтение отстаёт примерно в 62 раза,
500 точечных SELECT — в 130–175 раз, вставки в транзакции — в 131 раз.
Это разрыв всего стека API, а не доказательство такого же разрыва языков вообще.
Проверенный эксперимент с упрощением readers отклонён; результаты ниже в отдельном разделе.

## Условия

- CPython 3.9.6 из текущего окружения; это **не сравнение с последней версией Python**.
- Okkama 0.3.4, release, обычная сборка без заявленного PGO; IR, Sparrow JIT, JVM.
- macOS 26.5.2, arm64. Точные compiler/source hashes — в JSON результатов.
- SQLite **3.51.0 у обоих**: проверено через `SELECT sqlite_version()` у Okkama
  и `sqlite3.sqlite_version` у Python.
- 5 000 строк, три колонки: целое id, строка name, nullable nick. Каждая третья
  nick — NULL; среди остальных каждая пятая — пустая строка. NULL заменяется на
  `guest`, пустая строка сохраняется. SELECT отсортирован по первичному ключу.
- Основной прогон: пять процессов на конфигурацию. В каждом процессе каждая фаза
  сначала выполняется один раз для прогрева, затем один раз измеряется. Порядок
  движков чередуется; процессы работают последовательно, без параллельных замеров.
- Измерение внутри программы монотонными часами; компиляция и запуск процесса
  не входят в таблицу. Все контрольные суммы проверены независимой формулой.
- Python использует `sqlite3.Row`, обычное синхронное API и стандартный кэш SQL.
  Okkama — async worker, immutable snapshots, типизированные readers, Query/Param.
  Новая Python cursor не означает отключённый statement cache. Эти различия
  намеренно сохранены: сравнивается использование штатного API.

## Что установлено и что пока является гипотезой

1. **Проблема шире typed readers.** `scan_raw` вообще не вызывает `row.int/text/maybe`,
   но на Sparrow уже отстаёт примерно в 67 раз. В этот замер входят native fetch,
   создание Row/DbValue, управление async-курсором и накопление результата.
   Он не выделяет стоимость каждого из этих компонентов по отдельности.
2. **Чтение готовой строки тоже дорого.** В `projection_only` нет SQL в измеряемой
   части. Остаются typed readers, поиск колонок, Maybe, длины строк и накопление.
   Отставание Sparrow — около 47 раз. Это самостоятельная точка для оптимизации.
3. **Prepared API пока не даёт стабильного выигрыша.** На 500 SELECT Sparrow
   prepared медленнее обычного Statement, а на 1 000 SELECT — быстрее.
   Делать общий вывод «prepared всегда хуже» нельзя. Снимки параметров, слои
   вызовов, размеры выборки и прогрев JIT требуют отдельного исследования.
4. **Получение массива не исправляет разрыв.** `all(limit)` всё ещё получает строки
   через тот же async-контракт и дополнительно собирает результат. Оно не является
   native bulk-fetch API, эквивалентным одному вызову Python `fetchall()`.

По текущему коду видны кандидаты, но их доли времени ещё не измерены профайлером:

- `SqliteFrame.rows` создаёт значения, затем `Row` повторно проверяет колонки
  и снимает снимок значений для каждой строки.
- `ObservedDbValue` запускает printing/capture protocol; `DbValueCapture` содержит
  несколько Atomic и массивов. Typed reads создают ObservedDbValue заново.
- `Row.value(name)` строит массив совпадений через `filter` при каждом обращении.
- `int()` строит BigInt-границы и переводит число через строку при чтении.
- Query/prepared/driver повторяют снимки и упаковку параметров; native SQLite
  работает через очереди worker-заданий. Возможный вклад каждой стадии пока гипотеза.

## Приоритет следующей работы

1. **Профилировать `scan_raw` и точечный SELECT.** Разделить native worker,
   декодирование результата, Row construction, validation и async dispatch.
2. **Уменьшить повторную работу на границе драйвера.** Один проверенный снимок
   метаданных на result set и компактное представление уже проверенных значений.
   Не отключать проверки для внешних пользовательских DbValue/Sequencing.
3. **Упростить чтение уже проверенной строки.** Убрать повторный capture,
   промежуточные массивы поиска и лишние переходы через адаптеры; отдельно
   измерить затраты памяти, чтобы кэш не ускорил CPU ценой неконтролируемого RSS.
4. **Проверить пакетные операции.** Отдельный bounded bulk-fetch/execute-many
   может сократить async/worker переходы. Это расширение API, а не скрытое
   изменение поведения `next()` или обещание такого же выигрыша для PostgreSQL.
5. **После каждого изменения повторить этот набор и conformance.** Сохранять
   NULL, MissingColumn/AmbiguousColumn, диапазоны чисел, лимиты, отмену и cleanup.

## Ограничения

Это SQLite в памяти: диск/fsync, сетевые round trips и PostgreSQL здесь не измерены.
Python-драйвер PostgreSQL в текущем окружении не установлен. Live PostgreSQL
проверялся ранее на корректность, но эти успешные тесты не являются замерами скорости.

Ни RSS, ни allocation counts, ни CPU profile в данном прогоне не снимались.
Одного внутреннего прогрева недостаточно для утверждения о полном JVM steady state.
Порядок фаз фиксирован; нельзя вычитать `scan_raw` из `scan_stream` как точную
стоимость чтения колонок. Эти результаты не следует переносить на весь язык,
другую версию Python, дисковую БД или production-нагрузку.

## Проверка оптимизации readers: эксперимент отклонён

Повторный прогон 2026-11-02: пять пар before/after на каждый движок,
5 000 строк / 500 запросов. Порядок версий чередовался, процессы выполнялись
последовательно, без параллельных тестов. Обе версии использовали одинаковый
снимок stdlib, кроме `db/read.ok` и `db/row.ok`; before для этих двух файлов
соответствует `a24ec302192496311a3ea68bc5f5b6938226762b`.

Эксперимент убирал RowReader из строгих методов Row и заменял ParsedInt
прямым int_parse для канонической строки BigInt. Проверки диапазона signed
64-bit сохранялись. Все контрольные суммы совпали.

Медианы before → after, мс (это эксперимент, а не текущая реализация):

| Фаза | IR | Sparrow | JVM |
|---|---:|---:|---:|
| projection_only | 137.462 → 129.583 | 45.122 → 45.129 | 18.863 → 18.753 |
| scan_raw | 254.352 → 270.756 | 130.428 → 141.981 | 157.433 → 156.675 |
| scan_stream | 431.274 → 426.328 | 180.428 → 181.039 | 155.141 → 155.624 |
| scan_all | 480.303 → 460.748 | 219.490 → 222.883 | 161.083 → 158.740 |
| lookup_prepared | 146.750 → 141.717 | 136.544 → 140.031 | 157.062 → 146.404 |
| lookup_statement | 146.331 → 147.238 | 115.077 → 118.231 | 154.226 → 150.539 |
| insert_transaction | 51.182 → 52.203 | 45.942 → 46.587 | 51.008 → 49.750 |

Чтение готовой строки в IR сократилось на 5,7%; Sparrow не ускорился,
изменение JVM составило менее 1%. Полные сценарии не дали последовательного
выигрыша, часть медиан ухудшилась. Пять пар не доказывают причинность этих
ухудшений, но не дают оснований принимать изменение ради ускорения SQL/DB.
Оба изменения readers возвращены к исходной реализации. Большой разрыв
с Python остаётся; следующая цель — профилирование scan_raw и создания Row.

Первый эксперимент ошибочно заменял проверку диапазона на int_parse_valid.
Эта функция допускает числа произвольной длины и не проверяет signed 64-bit.
Conformance обнаружил четыре ошибки, поэтому `strict-read-optimized.json`
**невалиден для выводов об ускорении**: он измеряет нарушенный контракт,
к тому же часть прогона пересекалась с тестами. Этот файл сохранён только
как история отклонённого эксперимента.

В conformance сохранены три дополнительные проверки: underflow с сохранением
причины ошибки, underflow через Maybe и нормализация ведущих нулей.
Для исправленного эксперимента прошли 10 DB-кейсов на каждом из трёх движков,
в том числе 80 проверок row-readers.

## Нативное ядро DB: принятый перенос

Дата: 2026-11-02. Новый `runtime/db` хранит неизменяемые типизированные ячейки,
проверяет протокол пользовательского DbValue нативным приёмником, хранит общий
индекс имён колонок. SQLite передаёт int64/float напрямую в ячейки, без строкового
перехода через stdlib. Row больше не повторяет capture при каждом typed read и
не пересоздаёт схему для каждой строки штатного драйвера. Строки владеют данными
независимо от reply/cursor/connection. Размер пакета SQLite оставлен равным 8:
эффект изменения batch size в эти цифры не входит.

В IR/Sparrow работает общий Rust-provider; JVM имеет соответствующую реализацию
на Java, как в существующем JSON. PostgreSQL использует общий нативный capture,
ячейки и схему; **сетевая машина состояний, framing/auth и разбор текстовых
значений PostgreSQL в этом изменении не перенесены в Rust**. Query, управление
пулом/транзакциями и публичные ошибки также остаются в stdlib.

Метод: 5 чередующихся пар before/after на каждый движок, последовательно,
без фоновых сборок и тестов. 5 000 строк / 500 запросов, внутренний прогрев
каждой фазы. Before восстанавливает read/row/value/sqlite/postgres из
`a24ec302192496311a3ea68bc5f5b6938226762b`; остальные модули и release-компилятор
одинаковы. Старый stdlib использует совместимые legacy native getters нового
runtime: это сравнение путей API, а не исторических бинарников. Все контрольные
суммы совпали. Python повторно измерен пятью отдельными процессами после пар.

Медианы, мс. В ячейках Okkama: before → after (ускорение).

| Фаза | Python | IR | Sparrow | JVM |
|---|---:|---:|---:|---:|
| projection_only | 0.959 | 135.493 → 47.174 (2.87×) | 44.721 → 8.978 (4.98×) | 18.462 → 2.724 (6.78×) |
| scan_raw | 1.972 | 250.500 → 78.509 (3.19×) | 127.318 → 62.800 (2.03×) | 155.175 → 143.145 (1.08×) |
| scan_stream | 2.922 | 418.831 → 136.751 (3.06×) | 178.709 → 64.078 (2.79×) | 150.592 → 120.849 (1.25×) |
| scan_all | 3.107 | 462.279 → 144.951 (3.19×) | 218.237 → 65.237 (3.35×) | 174.721 → 124.541 (1.40×) |
| lookup_prepared | 0.791 | 141.111 → 120.215 (1.17×) | 134.393 → 127.441 (1.05×) | 148.953 → 146.696 (1.02×) |
| lookup_statement | 0.859 | 140.351 → 121.025 (1.16×) | 113.348 → 100.059 (1.13×) | 145.409 → 147.849 (0.98×) |
| insert_transaction | 0.333 | 49.096 → 51.024 (0.96×) | 44.395 → 41.673 (1.07×) | 48.273 → 50.987 (0.95×) |

Перенос даёт устойчивое крупное улучшение чтения готовых строк и полных выборок
на IR/Sparrow. На Sparrow потоковое чтение теперь около 22× времени Python
вместо примерно 61× в парном before. Разрыв остаётся большим. Точечные запросы
и вставки не получили сопоставимого улучшения; небольшие разницы, включая
ухудшения отдельных JVM/IR фаз, нельзя объявлять значимыми без дополнительных
замеров. Следующая работа должна измерять стоимость Query/prepared/worker и
повторной обработки параметров, а не обещать устранение разрыва одной правкой.

Проверки:

- 552 Rust workspace tests: PASS, без ignored. Запуск с RUST_MIN_STACK=16777216:
  на стандартном стеке существующий тест глубокой equality завершался stack
  overflow; при увеличенном стеке прошёл весь набор.
- 11 выбранных conformance-кейсов × IR/Sparrow/JVM: 33 PASS, включая JSON/SQLite
  exact-number, отмену, cleanup, pool, cardinality и границы чисел.
- Readers: 89 проверок, в том числе snapshot пользовательского printer,
  пропущенное/повторное событие, неверный kind, запрет записи после seal и UTF-8
  byte limit. SQLite дополнительно проверяет сохранность 17 строк через несколько
  пакетов после закрытия соединения: NULL, UTF-8 с NUL, bytes, float, int64 min.
- 2 живых PostgreSQL TEMP-сценария × 3 движка: 6 PASS. Это проверка корректности,
  а не PostgreSQL benchmark.
- Release-сборка и conformance validate: PASS.

RSS и число аллокаций пока не измерены. Один внутренний прогрев не доказывает
JVM steady state. Здесь не измерены диск, сеть или PostgreSQL throughput.

## Последующий этап: I/O и async

После нативного ядра дополнительно исправлены два лишних потока-посредника
SQLite (ответы/maintenance и барьер settled) и линейный поиск при регистрации
Future. В новом парном прогоне на Sparrow SELECT через Statement ускорился
ещё в 1,51 раза, вставки в транзакции — в 1,56 раза, поток/массив — в 1,34–1,38.
Готовые строки почти не изменились. Большой разрыв с Python остаётся.

[Разбор scheduler, послойные замеры, актуальное сравнение с Python и проверки](IO-ASYNC.md).

Последующий парный прогон с четырьмя прогревами: адаптивные пакеты строк,
пропуск лишнего барьера после подтверждённого ответа и однопроходные prepared
bindings дали на Sparrow 1,75× для raw scan, 1,53× для потока, 1,20× для prepared
lookup и 1,38× для вставок. Разрыв с Python остаётся примерно 10× на сканировании
и 60× на отдельных SELECT. Таблица, ограничения и направление переноса на тонкий
native API добавлены в [IO-ASYNC.md](IO-ASYNC.md).
