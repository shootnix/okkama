# SQL/DB: runtime и async — расследование 2026-11-02

**Подтверждены удержание закрытых результатов до завершения программы и значительные расходы обвязки над Rust-драйвером. Единственной причиной отставания планировщик не является.** Текущий публичный путь к SQLite пока нельзя считать тонким.

Исследован текущий SQLite/rusqlite на Sparrow и общий Rust runtime. PostgreSQL, MySQL/MariaDB, JVM, TLS и сетевой ввод-вывод этим исследованием не покрыты. На момент диагностики 2026-11-02 изменений рабочего runtime/stdlib не было: диагностические варианты запускались на отдельных временных копиях stdlib. Это результаты диагностики, не отчёт о внедрённых исправлениях.

**1. Высокий приоритет: закрытые SQL-ответы удерживаются глобальным реестром Future. Подтверждено кодом и памятью.**

Цепочка владения:

- `std/db/sqlite.ok:131`: каждый `reply()` создаёт `FutureGroup`, вызывает `group.start(waiting)`.
- `okkama-runtime-core/src/intrinsics.rs:1317`: группа вызывает `sched::register(&origin)`.
- `okkama-runtime-core/src/sched.rs:371`: реестр сохраняет сильный `Rc<FutureCell>` до завершения запуска.
- Завершённый Future сохраняет свой результат — native handle с `Rc<Reply>`.
- `okkama-runtime-core/src/native/sqlite.rs:1753`: `sqlite_reply_close()` меняет только `closed`; `Reply.data.rows`, BLOB и метаданные остаются в памяти.

Воспроизведение: свежий процесс, последовательно выполнять `Query(...SELECT zeroblob(1048576) AS payload).one()`, проверять `row.size()==1`, завершать область строки. Сравнение с временным вариантом `reply()`, который ожидает Future напрямую, а при незавершённом ответе вызывает отмену и ждёт worker barrier.

| Запросов по 1 МиБ | Текущий код, peak RSS | Без регистрации каждого ответа, peak RSS |
|---:|---:|---:|
| 10 | 33.7 МиБ | 24.0 МиБ |
| 80 | 109.0 МиБ | 24.1 МиБ |
| 160 | 193.9 МиБ | 25.5 МиБ |

Один запуск каждой точки, `/usr/bin/time -l`; peak RSS включает старт и компиляцию. Это удержание живыми ссылками до конца программы, а не доказательство утечки после её завершения. Для долгоживущего сервера эффект практически неограниченного накопления критичен. Построчный/пакетный лимит 8 МиБ не ограничивает сумму всех сохранённых ответов.

Исправления нужны на двух уровнях: закрытие ответа должно освобождать его payload; реестр supervision должен освобождать завершённые записи, которые больше не нужны для shutdown и диагностики. Нельзя просто заменить весь реестр слабыми ссылками: запущенные задачи должны доживать до завершения, а ненаблюдённые ошибки — сохраняться в определённом порядке. Также нельзя стирать пользовательское значение Future: повторный await обязан возвращать кэшированный исход.

Регрессии для будущего исправления: сохранённый Row переживает закрытие Reply; чтение закрытого handle отклоняется; повторный await, отмена, поздний ответ и очистка курсора работают; ненаблюдённые ошибки и их порядок сохраняются; рост количества запросов не даёт линейного накопления payload.

[Исходник воспроизведения и RSS](results/rusqlite-retention.json).

**2. Основной кандидат для улучшения CPU: управление графом объектов и слишком много промежуточных объектов. Подтверждён профиль; размер возможного ускорения ещё не измерен.**

Снят системный sample release-процесса: 5000 строк, 5000 lookup/insert, 4 прогрева, интервал 1 мс. Запрошено 10 секунд; процесс завершился раньше. Профиль включает прогрев и разные фазы, поэтому не является профилем одной операции.

В SQLite-worker 4540 из 4767 наблюдений попали в ожидание очереди (~95%). Среди горячих функций основного потока — `heap::collect`, хеширование указателей `Object`, `Value::clone`, операции регионов и выделение памяти. Это не процент CPU всего приложения: потоки, ожидающие события, тоже попадают в sample. Inclusive samples `sched::drive/complete/transfer` включают выполнение всей возобновлённой программы; их нельзя выдавать за собственные расходы планировщика.

`heap.rs:713` создаёт новый HashSet и рабочий Vec для обхода. `Region::register`, `transfer`, `begin_close` снова обходят достижимые графы; `begin_close` делает отдельный обход для каждого сохраняемого корня. Устранение одной промежуточной аллокации внутри обхода не устраняет сами повторные обходы.

Отдельный запуск `OKKAMA_JIT_STATS=1` на обычном наборе 5000/500 с прогревами зарегистрировал 1 735 798 выходов в помощник `obj.new`, 782 146 `region.enter`, 772 112 `region.leave`, 3 716 962 `call` и 245 687 `await`. Это счётчики JIT-помощников всего запуска, **не точное число всех объектов/аллокаций и не время CPU**. Времена инструментированного запуска не использовались для сравнения производительности.

Перспективные изменения: убрать временные объекты из успешного пути чтения полей; передавать готовую native-схему и набор cells; затем отдельно оптимизировать обход регионов с сохранением порядка destroy и передачи владения. Замена HashSet или отключение обхода без проверки семантики не является готовым исправлением.

[CPU profile gzip](results/rusqlite-cpu-sample.txt.gz), [JIT counters](results/rusqlite-jit-stats.txt).

**3. Архитектурный расход: короткий запрос проходит через много async-обёрток и несколько сообщений worker.**

Одинаковый SQL `SELECT 7 AS n`, 500 повторов, проверка ровно одной строки, 4 прогрева, медиана 5 запусков:

| Путь | Sparrow, мс |
|---|---:|
| 500 обычных вызовов | 0.056 |
| 500 простых async/await без I/O | 0.162 |
| Native API с типизированными параметрами и getters | 6.064 |
| Публичный SQLite driver, rows + проверка EOF | 25.327 |
| `Query.one()` | 34.277 |

Прямой native путь не создаёт публичные объекты строки/схемы и не воспроизводит весь lifecycle API. Разность времён не является точным счётчиком стоимости одной функции. Однако она показывает масштаб расходов над native boundary.

Минимальный Rust-тест без SQL: 500 ready Future — 0.021 мс; cold Future — 0.068 мс; доставок из постоянного worker напрямую — 1.485 мс. Generic `offload`, создающий поток на каждую операцию, — 7.699 мс. SQLite уже использует постоянный worker, поэтому обвинять его в создании нового потока на каждый запрос неверно.

Публичный `one()` проходит через `maybe`, `rows`, source adapter, connection, session, `rows_for`, `reply`, затем через `next/row/batch/reply`. Открытие курсора и первый fetch — отдельные ожидаемые worker-операции; release дополнительно ставится в очередь. Native benchmark также содержит open/fetch/release. Для микроскопических последовательных in-memory запросов расходы этих переходов существенны даже без SQL.

Кандидат на следующий архитектурный эксперимент: выполнить open + первый ограниченный fetch одним worker-заданием; native `one/maybe` может проверить вторую строку в том же задании. Сохранить правила занятости, транзакции, cancellation, ограничения размеров и ошибки cardinality. Выигрыш такого изменения пока не измерен. Для массовых вставок нужен отдельный сравнительный эксперимент с batching у обеих реализаций; нельзя сопоставлять наш batch с 500 отдельными вызовами Python и объявлять победу.

[Типизированные слои](results/rusqlite-typed-layers.json), [старый native API со строковой картой](results/rusqlite-layers.json), [Rust scheduler](results/rusqlite-async-delivery.txt).

**4. Измеренные локальные расходы: читатели полей, метаданные и lifecycle.**

Временные варианты запускались последовательно, в меняющемся порядке, 5 раз, 4 прогрева; контрольные суммы сверялись с baseline. Каждая строка ниже сравнивается со своим baseline того же эксперимента. Эффекты нельзя складывать.

| Диагностическое изменение | Сценарий | Baseline → вариант, мс | Снижение времени |
|---|---|---:|---:|
| Прямые native getters для `Row.int/text` | Уже полученная строка, 5000 чтений | 9.082 → 4.313 | 52.5% |
| То же | scan_stream 5000 строк | 32.006 → 26.751 | 16.4% |
| Убрать повторную stdlib-проверку/пересоздание Column | 500 prepared lookup | 40.607 → 37.297 | 8.1% |
| То же | 500 Statement lookup | 42.377 → 39.894 | 5.9% |
| Прямой await без FutureGroup на каждом reply | 500 вставок | 10.489 → 9.335 | 11.0% |
| То же | 500 Statement lookup | 42.056 → 40.736 | 3.1% |
| То же | 500 prepared lookup | 39.956 → 39.586 | 0.9% |
| Убрать предварительный snapshot PreparedQueryOpening | 500 prepared lookup | 40.607 → 39.870 | 1.8% |

**Это не готовые production-патчи.** Прямые getters меняют упаковку ошибок; metadata-вариант пропускает проверки; snapshot-вариант меняет момент фиксации внешнего DbValue. Последний небольшой эффект не следует считать устойчивым выигрышем без более точного эксперимента. Внедрять надо fast path с теми же контрактами, а не удалять проверки для всех входов.

Конкретные места:

- `std/db/row.ok` создаёт `DbColumnReader` для каждого strict getter. `std/db/read.ok` снова извлекает cell, проверяет kind, диапазон и вызывает getter; подробная ошибка нужна только на неуспешном пути.
- `SqliteFrame.columns()` создаёт Column; `DbRowSchema → DbColumns` повторно создаёт Column и проверяет UTF-8 размеры. Затем создаётся массив имён и native HashMap позиций.
- `PreparedQueryOpening` делает `DbValueSnapshot`; `SqliteBindings` повторно проходит через `ObservedDbValue`. Первый snapshot нужен по контракту, но canonical native cells должны проходить дальше без повторного пользовательского протокола.
- `Param(int)` делает `value.string() → BigInt`; захват integer снова передаёт строку в `db_integer`, где Rust её разбирает. Типизированный worker request избавил от последнего wire-формата, но не от всех преобразований выше него.
- `db_cells_bytes` форматирует числа для определения длины. Это отдельная оставшаяся стоимость, не повторная сериализация самого native запроса; её выигрыш отдельно не измерен.
- EOF в `SqliteRows.row()` представлен исключением `RowsEnded`, которое `QueryRows.next()` превращает в Maybe.none. Для one/maybe это регулярный успешный сценарий. Влияние исключений отдельно не изолировано; считать их главной причиной пока нельзя.

[Варианты reply/readers и точные diff](results/rusqlite-ablation.json), [metadata/snapshot и diff](results/rusqlite-metadata-snapshot-ablation.json).

**5. Что проверено и не подтвердилось как основное объяснение.**

Три запуска в меняющемся порядке:

- Отключение сборщика циклов: prepared lookup 40.414 → 40.182 мс, stream 31.811 → 31.568 мс. Многократного ускорения нет. `heap::collect` — обход владения регионами; `OKKAMA_GC=off` его не отключает.
- JIT threshold=1: prepared lookup 40.478 мс против 40.414 мс, stream 32.434 против 31.811 мс. Более ранняя JIT-компиляция проблему не устранила.
- Группы задач дают подтверждённое удержание памяти, но небольшую долю задержки коротких запросов. Исправить их необходимо, однако обещать после этого 1.5× от Python нельзя.

[Runtime probes](results/rusqlite-runtime-probes.json).

**Порядок дальнейшей работы:** сначала освобождение payload и ограничение supervision-реестра с тестами lifecycle; затем native successful-path для строк/схемы; затем объединение первого fetch с выполнением; после нового профиля — изменения управления регионами. Текущая цель 1.2–1.5× от Python не достигнута, и эти эксперименты не доказывают, что одних локальных правок достаточно.

Сырые JSON содержат замеры, временные варианты, исходники диагностических сценариев и/или скрипты воспроизведения. Абляции сохраняют diff относительно своего stdlib snapshot. CPU/RSS запускались отдельно от timing-серий. Полная безопасность нового rusqlite-драйвера, гонки отмены и вся conformance-матрица требуют отдельной проверки; данный документ не заменяет её.

**Исправление 2026-11-03: освобождение закрытого Reply.**

Rust Reply теперь хранит payload в RefCell<Data>; закрытие очищает весь Data. JVM Reply заменяет data пустой картой. Выданные cells являются самостоятельными снимками, поэтому остаются доступны. Состояние закрытого handle и кэширование Future не изменены. Реестр завершённых Future пока не изменён: остаётся отдельная задача по освобождению самих записей, даже когда крупный payload уже освобождён.

Повторный RSS-тест с исходным stdlib и новой release-сборкой:

| Запросов по 1 МиБ | До исправления | После |
|---:|---:|---:|
| 10 | 33.7 МиБ | 23.4 МиБ |
| 80 | 109.0 МиБ | 23.4 МиБ |
| 160 | 193.9 МиБ | 24.8 МиБ |

Один запуск каждой точки, тот же workload; измеряется peak RSS целого процесса. Это подтверждает устранение линейного накопления больших закрытых payload на данном сценарии, а не полное отсутствие удержания памяти во всём runtime. [Новые сырые замеры](results/rusqlite-retention-fixed.json).

Проверки: 49 unit-тестов runtime-core с RUST_MIN_STACK=16777216; 11 выбранных SQLite/exact-number conformance-сценариев на каждом из IR, Sparrow и JVM (33 PASS); validate 833 cases OK; release-сборка успешна. Новый unit-тест удерживает Reply через завершённый зарегистрированный Future, проверяет освобождение payload, закрытый handle и независимость ранее выданных text/blob cells. Новый conformance `L11.sqlite.closed-reply-row` проверяет integer/text/blob/null после закрытия курсора и соединения. Первый запуск полного unit-набора с обычным размером стека завершился stack overflow в существующем equality-тесте; повтор с указанным размером стека прошёл.

**Исправление 2026-11-03: освобождение записей supervision-реестра.**

Реестр теперь хранит активные Future и ненаблюдённые ошибки. Успешный или отменённый Future удаляется при завершении; завершившийся с ошибкой — после observe/await. Наблюдённая, но ещё активная задача остаётся зарегистрированной для shutdown. Значения и ошибки внутри пользовательского Future не стираются: повторный await сохраняет прежний исход.

Rust использует BTreeMap по монотонному номеру регистрации и HashMap идентичностей для удаления; порядок ошибок не зависит от порядка завершения. Удалённые записи не оставляют растущего массива пустых слотов. JVM использует LinkedHashSet и тот же критерий освобождения. Регистрация уже завершённого успеха, отмены или наблюдённой ошибки не удерживает Future заново.

Сравнение прежней release-сборки (уже с очисткой Reply) и новой, один процесс на точку: spawn короткой задачи, два await с проверкой результата, затем следующая задача. Peak RSS:

| Завершённых задач | До | После |
|---:|---:|---:|
| 1 000 | 12.5 МиБ | 12.3 МиБ |
| 10 000 | 14.0 МиБ | 12.3 МиБ |
| 50 000 | 28.1 МиБ | 12.3 МиБ |

Это измерение конкретного последовательного сценария, не обещание постоянной памяти при растущем числе активных задач или ненаблюдённых ошибок. [Исходник, хеши сборок и RSS](results/future-registry-retirement.json).

Парные SQL-замеры: 5 пар на IR и Sparrow, 4 прогрева, одинаковый stdlib. Sparrow: prepared lookup 40.384 → 40.383 мс, Statement lookup 43.263 → 42.828 мс, streaming 31.690 → 32.130 мс, вставки 10.526 → 10.574 мс. Медианы по всем фазам двух движков изменились примерно от −2.9% до +1.4%; значительного ускорения SQL эта правка не дала. [Все пары и контрольные суммы](results/future-registry-db-paired.json).

Проверки: 53 unit-теста runtime-core с RUST_MIN_STACK=16777216; 91 conformance-сценарий (L07, L08, L11.sqlite, L12.future) на каждом из IR, Sparrow и JVM — 273 PASS; release и JVM runtime собраны. Новые unit-тесты проверяют освобождение 20 000 Future через Weak, кэшированный исход, порядок ненаблюдённых ошибок, позднее наблюдение, shutdown активной наблюдённой задачи, отмену холодной задачи и регистрацию из completion listener. Следующий этап — упрощение DB-обвязки; данным исправлением она не менялась.

**Упрощение DB-обвязки 2026-11-03: прямое чтение int/text.**

`Row.int()` и `Row.text()` теперь читают подходящую native-ячейку напрямую, без создания DbColumnReader на успешном пути. `db_int_valid` проверяет и тип, и диапазон; text проверяет native kind. Неуспешная проекция использует прежний DbColumnReader, сохраняя RowValueFailure, actual_kind и cause. Поиск столбца остаётся общим: MissingColumn/AmbiguousColumn не оборачиваются. Публичные сигнатуры и native ABI не изменены; Maybe/Presence и остальные getters пока используют прежний путь.

5 пар на каждом движке, 4 прогрева, один release-компилятор, отдельный снимок прежнего stdlib; Python измерялся в каждой серии. Медианы, мс:

| Фаза | Sparrow до | Sparrow после | IR до | IR после | Python |
|---|---:|---:|---:|---:|---:|
| Уже полученная строка, 5000 чтений | 9.422 | 4.718 | 47.592 | 23.559 | 0.964 |
| scan_stream | 32.739 | 28.000 | 106.966 | 81.968 | 2.999 |
| scan_all | 33.205 | 28.956 | 111.362 | 90.594 | 3.288 |
| lookup_prepared | 41.122 | 40.663 | 73.017 | 67.875 | 0.766 |
| lookup_statement | 42.592 | 41.668 | 70.056 | 66.116 | 0.876 |

Чтение готовой строки ускорилось примерно вдвое, время Sparrow streaming снизилось на 14.5%. Короткие запросы остаются существенно медленнее Python: prepared примерно 53×, Statement примерно 48×. Устранение всего DB overhead этим шагом не достигнуто.

Контрольные фазы: Sparrow scan_raw 19.847 → 20.011 мс, вставки 10.757 → 10.775 мс; IR scan_raw 43.947 → 45.738 мс, вставки 20.985 → 20.871 мс. В том числе сохранено ухудшение медианы IR scan_raw на 4.1% в этой серии: эта фаза не вызывает изменённые getters, причинность такого отклонения отдельно не установлена. Python SQLite 3.51.0, Okkama SQLite 3.50.2; сравнение характеризует публичные API в in-memory workload, а не одинаковые реализации SQLite.

Проверки: 12 выбранных conformance-сценариев L09.db, L11.sqlite, L12.exact-number-json-sqlite на IR/Sparrow/JVM — 36 PASS; validate 833 cases OK. Добавлены 8 проверок подробностей ошибок типа, NULL, запрета преобразования boolean в int, отсутствующих/неоднозначных столбцов и Unicode. Цель 1.2–1.5× не достигнута. Python использует синхронный sqlite3, Okkama — async worker; версии SQLite также различаются (Python 3.51.0, Okkama 3.50.2). Это результат пользовательских API, не изолированная оценка языка или планировщика.

Для следующего диагностического эксперимента предлагается inline-исполнение того же SQLite backend с сохранением SQL, параметров, native cells, Row, Query и числа открытий/fetch. При этом native Future уже завершён при await. Такой вариант изолирует очереди и межпоточные пробуждения, но сохраняет создание Future и async-обёртки Okkama. Полностью синхронный API был бы отдельным вторым экспериментом: смешивать оба изменения в одном измерении нельзя. Inline-режим блокирует event loop и меняет доступность отмены во время SQL, поэтому его замеры не являются подтверждением корректности production cancellation. Этот режим в данном шаге ещё не реализован.
