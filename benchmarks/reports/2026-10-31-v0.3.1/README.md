# Бенчмарки Okkama 0.3.1 — 31 октября 2026

Замер перед релизом 0.3.1: общий набор (три движка Okkama против тех же
программ на Python, Perl и Ruby) и отдельно — JSON, главная работа релиза.
Все таблицы общего набора — в [REPORT.md](REPORT.md), сырые замеры — в CSV и
JSON рядом, программы JSON-замера — в [json/](json/).

## Итог

**JSON стал быстрее в 21–26 раз.** Чтение 10 000 заказов (2.7 МБ) в объекты
и запись обратно: 7.0 с в 0.3.0 → 0.33 с (обычная сборка) → 0.27 с (PGO).
Python 3.9 со своим `json` на C делает это за 55 мс: отставание ×4.9, а на
50 000 заказов — ×2.6. Разбор у Okkama быстрее, чем у Python.

Общий набор — без изменений, кроме `05-strings` (1.23× за счёт дешёвых
вызовов natives). Среднее геометрическое отношений медианного wall-time по
тестам 01–10 (больше 1 — Okkama быстрее):

| | Python 3.9 | Perl 5.42 | Ruby 2.6 | Okkama JVM |
|---|---:|---:|---:|---:|
| **Sparrow с JIT** | **2.36×** | **2.40×** | **1.75×** | **1.85×** |
| Sparrow без JIT | 0.78× | 0.70× | 0.58× | 0.61× |
| Okkama IR | 0.51× | 0.44× | 0.38× | 0.40× |

В 0.3.0 у Sparrow с JIT было 2.31× к Python.

### Где мы проигрываем

| Тест | Sparrow с JIT | Лучший | Отставание |
|---|---:|---|---:|

| 06-collections | 0.091 с | Perl 0.049 с | 1.9× |
| 09-closures | 0.299 с | Okkama JVM 0.209 с | 1.4× |

## JSON

Документ `{"orders": [...]}`: у заказа номер, клиент (вложенный объект),
сумма строкой, признак оплаты, теги и три позиции. Программа читает файл,
разбирает его, раскладывает в объекты `Order`/`Line` (сумма — `Decimal`),
строит `JsonValue`-дерево и пишет компактный текст. Время стадий — часы
внутри программы (запуск процесса не входит): у Okkama медиана 5 запусков
(JVM — второй из двух), у Python — лучший из 5 повторов в одном процессе.

**10 000 заказов (2.7 МБ):**

| Стадия | Python 3.9 | 0.3.0 | 0.3.1 | 0.3.1 + PGO | 0.3.1 JVM |
|---|---:|---:|---:|---:|---:|
| разбор | 19 мс | 21 мс | 21 мс | **17 мс** | 69 мс |
| в объекты | **12 мс** | 1 934 мс | 156 мс | 128 мс | 56 мс |
| дерево + текст | **24 мс** | 5 030 мс | 150 мс | 125 мс | 122 мс |
| **всего** | **55 мс** | **~7 000 мс** | **327 мс** | **270 мс** | **247 мс** |

**50 000 заказов (14 МБ):**

| Стадия | Python 3.9 | 0.3.1 | 0.3.1 + PGO | 0.3.1 JVM |
|---|---:|---:|---:|---:|
| разбор | 120 мс | 101 мс | **86 мс** | 198 мс |
| в объекты | **133 мс** | 468 мс | 402 мс | 155 мс |
| дерево + текст | **126 мс** | 576 мс | 492 мс | 439 мс |
| **всего** | **379 мс** | **1 145 мс** | **979 мс** | **792 мс** |

- Разбор (Rust) быстрее Python. Запись и чтение в объекты медленнее: Python
  выполняет `json.loads` и поиск в словаре в C, а у нас обращение к полю —
  несколько вызовов и временных объектов (`JsonView`, чтение, natives).
- JVM лучше всего создаёт объекты: в 3 раза быстрее Sparrow и почти как
  Python на 50 000 заказов. Разбор и запись у неё медленнее (natives на Java),
  а запуск и прогрев добавляют 150–200 мс к wall-time.
- Что дало ускорение — раздел Performance [CHANGELOG](../../../CHANGELOG.md):
  нативный разбор чтением узлов без лишних объектов, нативные экранирование,
  числа и буфер вывода, удаление пустых регионов владения, вызов natives
  без SipHash и разбора символов.

## PGO

`make pgo` собирает бинарники с оптимизацией по профилю
(`okkama-rs/tools/pgo/build.sh`). Отношение ко времени обычной сборки, те же
программы:

| | обычная | PGO | выигрыш |
|---|---:|---:|---:|
| JSON 10 000 заказов (стадии) | 326 мс | 270 мс | 17% |
| JSON 50 000 заказов (стадии) | 1 145 мс | 979 мс | 14% |
| общий набор 01–10 (геом. среднее) | | | 7% |

Самые большие выигрыши: `05-strings` 1.21×, `06-collections` 1.13×,
`10-app` 1.11×; на `01-arith` и `04-bigint` — около 1%. Обучение и замер
общего набора используют одни программы, поэтому 7% может быть завышено;
JSON-обучение шло на других данных (1 000 заказов, собранных в коде).

Таблицы общего набора выше — обычная release-сборка, как в пакетах релиза.

Флаги, которые не дали выигрыша: `-C target-cpu=apple-m1` (базовый для
Apple Silicon) и `native` (M2) — в пределах шума, `lto = "thin"` — на 1%
медленнее `fat`. `panic = "abort"` дал 5% на JSON, но превращает
внутренние ошибки в аварийное завершение, а JIT использует перехват паники
как запасной путь, поэтому сборка оставляет раскрутку стека.

## Как измерено

- Apple M2 Max, 32 GiB, macOS (Darwin 26.5.2); release-сборка с fat LTO,
  `okkama 0.3.1`.
- Общий набор: 10 замеров каждой пары «тест × движок» после одного
  прогревочного, `benchmarks/run.py --runs 10`; вывод всех семи
  конфигураций совпадает во всех 11 тестах.
- «До» ([before.json](before.json)) — прогон отчёта 0.3.0.
- JSON: [json/generate.py](json/generate.py) создаёт данные,
  [json/orders.ok](json/orders.ok) (путь к файлу — вместо `__FILE__`) и
  [json/orders.py](json/orders.py) — программы.

Оговорки:

- Python 3.9 и Ruby 2.6 — системные версии macOS; Python 3.11+ и Ruby 3.x с
  YJIT заметно быстрее.
- У Perl `Math::BigInt` без GMP: `04-bigint` исключён из среднего для Perl.
- В Perl и Ruby нет `async`: котировка в `10-app` — обычный вызов.
