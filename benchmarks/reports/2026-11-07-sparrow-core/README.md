# Новое ядро Sparrow: бенчмарки 2026-11-07

Промежуточный отчёт (не релиз): `sparrow-next` на новом ядре (`crates/sparrow-core`)
против прежней VM Sparrow (origin), Okkama JVM, Python, Perl и Ruby. Таблицы —
[REPORT.md](REPORT.md) (сгенерирован `export.py`), сырые замеры — `results.json`,
прошлый отчёт для сравнения — `before.json` (0.3.3, 2026-11-01).

Как снято: `benchmarks/run.py --runs 10 --engines sparrow-core,sparrow,jvm,python,perl,ruby`,
компилятор и std из репозитория (std целиком на error enum), обычная release-сборка
без PGO, каждый запуск ограничен по CPU и по времени. Машина во время замеров была
под фоновой нагрузкой (load average ≈ 3): Python и origin медленнее, чем в 0.3.3,
примерно на 10%, поэтому сравнивать стоит отношения, а не абсолютные секунды.

## Выводы

- Новое ядро в среднем (геометрически по тестам 01–10) **в 5.4 раза быстрее
  Python**, в 6.1 — Perl, в 4.0 — Ruby, в 4.3 — Okkama JVM. Прежняя VM Sparrow — в
  2.7 раза быстрее Python; ядро быстрее неё вдвое.
- Сильнее всего ядро выигрывает на вызовах, объектах, ролях и замыканиях
  (02-calls 18.6×, 07-objects 17.2×, 08-roles 8.7×, 09-closures 5.8× против
  Python): прямые машинные вызовы и объекты как указатели на поля.
- Приложение (10-app: шесть модулей, роли, ошибки домена, async) — 3.4× быстрее
  Python и 1.9× быстрее прежней VM.
- Слабые места: 04-bigint — арифметика `num-bigint`, ядро на 20% медленнее прежней
  VM (там своя длинная арифметика); 05-strings и 06-collections — на уровне Python
  (1.4–1.5×); запуск 10 мс против 8 мс у прежней VM.
- Память: медиана RSS 16 МиБ (прежняя VM 10, Python 11, JVM 244).

## База данных (SQLite в памяти, Okkama против Python)

`benchmarks/db` (5000 строк, 500 точечных запросов), чередованием в клетке, мс:

| Сценарий | Python | origin 0.3.4 | ядро, утро | ядро, вечер |
|---|---:|---:|---:|---:|
| projection_only | 2.5 | 14.1 | 5.3 | 13.5 |
| scan_raw | 4.3 | 60.0 | 17.2 | 18.1 |
| scan_stream | 6.8 | 86.5 | 28.7 | 40.3 |
| scan_all | 7.0 | 85.6 | 31.1 | 34.4 |
| lookup_prepared | 2.0 | 92.0 | 24.0 | 44.0 |
| lookup_statement | 2.2 | 93.1 | 30.7 | 28.5 |
| insert_transaction | 0.7 | 26.6 | 8.0 | 10.2 |

Ядро быстрее origin в 3–9 раз; от Python отстаёт от 2–4 раз на чтении до 10–20 на
точечных запросах и вставке (переход в поток SQLite на каждый запрос — открытая
задача). Вечерний столбец снят на том же std после миграции ошибок и на шумной
машине; разброс между прогонами доходит до 2× на коротких фазах
(`projection_only`, `lookup_prepared` — в них попадает или не попадает сборка
мусора). По ходу найден и исправлен обрыв: кадры async-функций больше 32 слов
выделялись отдельно на каждый вызов (мигрированный `std/db` перешёл этот край в
`QueryRows.next`, вставка замедлилась вдвое); теперь классы размеров до 128 слов.
Чистые цифры БД — повторить на ненагруженной машине.
